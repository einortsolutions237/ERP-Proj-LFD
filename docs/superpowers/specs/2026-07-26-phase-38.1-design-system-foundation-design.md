# Phase 38.1 — Enterprise Design System Consolidation & Premium UI Modernization (Foundation)

## Purpose

Not a feature phase, not a business-logic phase, not a refactor. This phase exists to make the ERP feel like one cohesive enterprise product — visually — without touching any API, Firestore query, transaction, permission check, Cloud Function, or data model.

Given the scope of "every screen in the app," this work is deliberately split:

- **Phase 38.1 (this phase)**: build the shared design-token layer and a small internal primitives library, and prove both against two representative screens.
- **Phase 38.2+ (separate, later phases)**: roll the resulting system out module-by-module across the rest of the app (POS/inventory, CRM, clinical, HR, accounting, messaging, reports, admin). Each gets its own plan and completion report, matching this project's existing per-phase pattern.

This decomposition exists because a single phase attempting both the foundation and the full-app rollout would be unreviewable as one unit and impossible to revert cleanly if something in the foundation needed to change after the first real usage.

## Design direction

Confidence, clarity, professionalism, trust, precision, calmness — premium enterprise software. Visual inspiration only (Stripe Dashboard, Linear, Vercel Dashboard, Notion, Atlassian Admin, Raycast, GitHub Enterprise, Figma Enterprise) — copy nothing, adopt principles only.

Explicitly NOT in scope, this phase or any follow-on rollout phase under this initiative:
- No shadcn/ui adoption, no Tailwind replacement.
- No new hues — every token below derives from the existing marine/brass/mist/slate/success/danger/warning/info palette.
- No API, Firestore, permission, or Cloud Function changes.
- No responsive/breakpoint redesign (see "Verification" below for why).
- No accessibility overhaul beyond regressions this work might introduce.

## Current state (confirmed by direct inspection)

- `src/app/globals.css` (55 lines) defines only color tokens, one shadow (`--shadow-card`), and font-family tokens. No type scale, no radius scale, no tint/shade steps, no component-level classes.
- No `tailwind.config.*` — this is Tailwind v4, CSS-first config via `@theme inline`.
- No shared primitive components exist anywhere in `src/components/`. ~60 component files exist, all feature-scoped (`StaffTable`, `ProductForm`, `CheckoutForm`, etc.) — buttons, cards, badges, and alerts are hand-rolled inline with Tailwind classes, independently, screen by screen. This is the root cause of the visual drift the phase brief describes.
- Icons are custom inline SVGs (`src/components/dashboard/icons.tsx` shows the existing pattern: a shared `ICON_SVG_PROPS` constant, 24x24 viewBox, stroke-based) — no icon library dependency (`lucide-react`, `heroicons`, etc. all absent from `package.json`). Icon sizing will be standardized via a consistent className convention applied through the primitives, not a new library.

## New design tokens (`globals.css`, additive only)

- **Type scale**: `--text-page-title`, `--text-section-title`, `--text-card-title` — bundled size/weight/line-height/tracking values, closing the "consistent heading hierarchy" and "spacing between headings" requirements.
- **Radius scale**: `--radius-card`, `--radius-control` (buttons/inputs), `--radius-badge` (pill) — currently undefined; every screen today picks its own radius ad hoc.
- **Shadow scale**: expands the single `--shadow-card` into `--shadow-card`, `--shadow-card-hover`, `--shadow-popover` — needed for card hover-elevation.
- **Tint/shade steps** for marine, brass, success, danger, warning, info: each gets a `-subtle` (background) and `-strong` (text/icon) pairing. Badges, alerts, and hover/active states all consume these, so (for example) a badge's "success" background and an alert's "success" background come from one shared definition instead of two screens independently picking similar-but-different green values.

No existing token's meaning changes. `--color-marine` is still marine. This is purely additive.

## Primitives library (`src/components/ui/`, new directory)

- **`Button`** — variants `primary | secondary | ghost | danger | success`, plus an icon-only mode (square, matches text-button height), a `loading` state (spinner replaces label without changing button width, no layout shift), and `disabled`. One implementation for every button in the app.
- **`Card`** — default + `nested`/`subtle` variant (for a card inside a card, e.g. a widget inside a dashboard section), built on the new radius/shadow tokens. Hover elevation is a boolean prop, not per-screen copy-paste.
- **`Badge`** — semantic variants `success | warning | error | info | neutral`, built on the tint/shade tokens, with a `tone`-only mode so domain-specific badges (inventory/clinical/finance/HR/messaging status pills) map onto these same five colors with their own label text, rather than inventing new badge colors per module.
- **`Alert`** — `success | warning | error | info`, plus the app's two specialized cases (offline-sync recovery, permission-denied) rendered through the same component with a different icon/tone rather than one-off markup.
- **`PageHeader`** — title, optional description, optional primary-actions slot, optional filters slot. Structurally encodes the brief's "Title → Description → Actions → Filters" page rhythm so a screen can't easily drift from it by omission.
- **`StatTile`** — the Dashboard's stat-card shape (number + label + optional trend/icon).

**Deliberately deferred to Phase 38.2, not built now**: a `Table` shell (row height, sticky header, sort indicators, pagination, empty/loading states) and a `FormSection`/field-grouping primitive. Neither proof screen (Dashboard, POS/Checkout) is a data-table or long-form screen — building these now means designing them with no real usage to validate against. 38.2 targets a table-heavy and form-heavy screen specifically so these two get designed against something real, not guessed at.

## Proof screens and migration

- **Dashboard** (`src/app/(dashboard)/dashboard/page.tsx`, `src/components/dashboard/*`): stat tiles → `StatTile`; widget cards → `Card`; inline banners → `Alert`; low-stock/pending-count indicators → `Badge`; page header → `PageHeader`.
- **POS/Checkout** (`src/app/(dashboard)/pos/**`, `src/components/pos/CheckoutForm.tsx`, `QueueStatusIndicator.tsx`, offline-sync popover): cart/checkout buttons → `Button` (including the primary "Complete Sale" and danger "Void" cases); offline-sync/permission alerts → `Alert`; cart/payment badges → `Badge`. Highest-traffic screen in the app, so it's the real stress test for the Button and Alert variants.

No other screen is touched in this phase.

## Verification

- Standard-desktop-viewport visual review via `claude-in-chrome` screenshots, before/after, on both proof screens. `claude-in-chrome` connected cleanly through Phases 37 and 38 — expected to work here too.
- The `resize_window`/breakpoint-verification tool gap (open 3 phases running: 24, 36, 38) is explicitly **not** addressed by this phase and not worked around — responsive redesign is out of scope here, so it stays exactly as open as CLAUDE.md already records it, for whichever future phase actually tackles responsive layout.
- `npm run build` and the existing test suite (505 tests as of Phase 38) must both pass after migration. Since this phase only touches `.tsx`/`.css` presentation, no business-logic test should be affected — but any test that snapshot-tests markup or class names on the two proof screens needs to be updated deliberately if it breaks, not silently patched to pass.
- Zero Firestore/API/permission/Cloud-Function files touched — confirmed by review before the completion report is written.

## Completion report

Same format and location this project already uses (`docs/superpowers/plans/`): what tokens were added, each primitive's final API, what was migrated on the two proof screens with before/after confirmation, what's explicitly deferred to 38.2 (Table/FormSection primitives, every other module), and a final consistency-sweep note confirming no duplicate component was created and no screen outside the two proof screens was touched.
