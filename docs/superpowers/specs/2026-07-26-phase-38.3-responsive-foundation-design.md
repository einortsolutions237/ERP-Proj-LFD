# Phase 38.3 — Responsive & Accessibility Foundation (Design)

## Purpose

The pasted "Phase 38.3 / Responsive Excellence, Accessibility & Production Polish" prompt spans a scope that matches what had previously been split across a planned 38.3–38.5 sequence (Table/FormSection primitives, Navigation/Search, Mobile-prep/Performance/Audit) — plus a full WCAG AA accessibility audit never previously scoped at all. Per explicit direction, that older 38.3–38.5 outline is discarded; this prompt's scope becomes the new roadmap, decomposed into its own sequence:

- **Phase 38.3 (this phase)** — Responsive & accessibility foundation: the Table sticky-column pattern, the `FormSection` primitive, and a reusable focus-trap hook applied to the app's two existing modal-adjacent UIs.
- **Phase 38.4** — Responsive rollout across the rest of the app's screens, including the Dashboard specifically across desktop/tablet/mobile as its own named deliverable.
- **Phase 38.5** — Full WCAG AA accessibility pass (contrast, keyboard nav, focus visibility, aria labels, landmarks, form labels, error announcements, modal focus trapping, toast announcements, reduced motion).
- **Phase 38.6** — Performance + final design-consistency audit (UI/UX Pro Max → Impeccable → full audit → corrections → final verification), closing out the whole initiative.

Numbering note: the pasted prompt's header said "Phase 38.3" but its body said "Phase 40 begins ONLY after those phases are complete" — the same template-residue inconsistency as the prior two phases' prompts. Tracked as **38.3** per the header.

## The viewport-verification problem — resolved, not deferred again

Before any responsive design work, the prompt's own requirement to "resolve the viewport verification problem" was investigated directly, not assumed. Result: **there is no automated way to verify viewport/responsive behavior in this environment.** `resize_window` was retried at multiple target sizes, on both an existing tab and a freshly-created one resized before navigation — the tool reported success every time, but `window.innerWidth`/`innerHeight` (checked independently via `javascript_tool`) never changed from the OS display baseline (1536×730), a 4th consecutive identical failure after Phases 24, 36, and 38. No Chrome DevTools Protocol device-emulation tool exists in this toolset beyond the broken `resize_window`, and no Playwright is installed or available anywhere in this project or environment.

**Resolution, decided explicitly rather than deferred a 5th time**: this phase (and 38.4/38.5/38.6, wherever responsive claims are made) uses **manual human-in-the-loop verification** — at defined checkpoints, the user is asked to resize a real browser window (or check a physical device) and report what they see. This is the only channel that currently produces real, trustworthy verification. Every responsive claim in this phase's completion report will be backed by an actual manual check, named as such — not a tool's self-reported success, and not unverified static-analysis reasoning.

## Investigation findings (before any new work)

A codebase audit (not assumption) found:

- **Tables already scroll safely** — `NavShell.tsx`'s `<main>` wraps all page content in `overflow-x-auto`, and individual table components (checked: `ProductTable.tsx`, `StaffTable.tsx`) additionally wrap their own `<table>` in a local `overflow-x-auto` (redundant but harmless). No fixed pixel widths exist on any table — only `max-w-[Xrem] truncate` on individual cells with a `title` tooltip fallback, a deliberate, working pattern. **Already fine.** **Real gap**: zero sticky columns, zero expandable rows, zero detail-drawer pattern anywhere — "never destroy information" today just means "make the user scroll," not a deliberate strategy.
- **Forms are already mobile-safe** (single-column stacking, `min-h-11` touch targets from Phase 38's earlier fix) but have **zero responsive grouping** — every form looks identical regardless of viewport, an intentional-per-viewport gap rather than a breakage.
- **No modal/dialog component exists anywhere in this app.** The only `fixed inset-0` match in the whole `src/` tree is `NavShell.tsx`'s own mobile nav drawer. `DeleteCustomerButton.tsx` uses the browser-native `confirm()` (no custom overlay, so no focus-trap question applies — native dialogs handle their own focus). The only two modal-*adjacent* UIs are `QueueStatusIndicator.tsx`'s popover and `CheckoutForm.tsx`'s inline customer-picker panel — **neither traps focus today**, and there is no larger hidden inventory of broken dialogs to find.
- **The Dashboard's widget grid is already responsive** (`grid grid-cols-1 gap-4 md:grid-cols-2`, confirmed in `dashboard/page.tsx`) — whether it *feels* intentionally designed per viewport versus just reflowing is a 38.4 judgment call, not a structural fix needed now.
- **Labels are well-covered** (125 `<label` instances across 38 files) but **`aria-label` is thin** (10 instances across 7 files) — icon-only buttons in particular likely lack labels broadly; a real gap, but a 38.5 (full WCAG AA pass) concern, not this phase's.
- **`aria-live` is implicit-only** — `Alert`/`ToastProvider` (built in Phases 38.1/38.2) use `role="alert"`/`role="status"`, which carry implicit `aria-live="assertive"`/`"polite"` per the ARIA spec. Arguably already fine; worth a real screen-reader confirmation in 38.5, not rebuilding now.

Because of these findings, this phase's real scope is three concrete, well-bounded deliverables — not a ground-up responsive rebuild.

## Scope shape

Same foundation-then-proof-screens shape as every prior phase in this initiative.

### 1. Sticky-column table pattern (not a new component)

Building a fully generic, column-configurable `<Table>` abstraction now would be premature — the actual gap is a specific, well-understood technique (a sticky first column), not a swappable table architecture, and only one real screen is being proven against it so far. This is deliberately **not** a new `src/components/ui/Table.tsx` file; it's a documented Tailwind pattern applied directly to `ProductTable.tsx`'s existing markup: the first `<td>`/`<th>` (Name) becomes `sticky left-0 z-10 bg-surface border-r border-mist`, and the row gets `group` so the sticky cell can pick up the same `group-hover:bg-mist/40` tint the rest of the row already shows on hover — otherwise the sticky cell would look visually disconnected while scrolling. Everything else about the table (scroll behavior, cell truncation, empty state) is untouched. Expandable rows and detail drawers are explicitly not built in this phase — deferred until a screen's real column count/density justifies the added complexity.

### 2. `FormSection` primitive

`src/components/ui/FormSection.tsx` — a thin grid wrapper (`grid grid-cols-1 gap-4 md:grid-cols-2`) for grouping related fields, collapsing to one column on mobile (matching current, already-safe behavior) and pairing up at `md+`. Proven on `StaffForm.tsx`: the form container widens from a fixed `max-w-md` to `max-w-md md:max-w-2xl` to give the 2-column grid room, and related fields are grouped (name+email, role+department, phone+address, start-date+status, qualifications+base-salary). The emergency-contact `fieldset` and the submit/cancel button row are left as single-width — grouping every field indiscriminately isn't the goal, grouping *related* fields is.

### 3. `useFocusTrap` hook

`src/hooks/useFocusTrap.ts` — a hand-built hook (no dependency) that, given an `active: boolean`, returns a ref to attach to an open panel's container. While active, it confines `Tab`/`Shift+Tab` cycling to the panel's focusable elements and returns focus to whatever triggered the panel's opening when it closes. It deliberately does **not** duplicate `Escape`-key or click-outside dismissal — both `QueueStatusIndicator` and `CheckoutForm`'s customer-picker already implement those independently; this hook adds only the missing piece (focus containment + return). Applied to both of the app's only two modal-adjacent UIs, its two real, existing consumers — not a hypothetical future modal.

### 4. Incidental primitive migration

While `ProductTable.tsx`'s page and `StaffForm.tsx`'s page are already being touched for the above, their buttons/headers are migrated onto the existing `Button`/`PageHeader` primitives (from Phases 38.1/38.2) in the same pass — avoiding a second future touch of the same files, consistent with this project's "reuse, don't duplicate" rule.

## Out of scope for this phase (explicitly deferred)

- A generic, column-configurable `Table` component — deferred until more real screens justify its shape.
- Responsive rollout to any screen besides `ProductTable`'s page and `StaffForm`'s page — Phase 38.4.
- The full WCAG AA audit (contrast, comprehensive aria-label coverage, screen-reader landmark review, error-announcement review) — Phase 38.5.
- Performance work and the final UI/UX Pro Max + Impeccable consistency audit — Phase 38.6.
- No API, Firestore, permission, or Cloud Function changes anywhere, per every phase in this initiative.

## Verification

- `npx tsc --noEmit` / `npm run build` for all new/changed code.
- Full existing test suite (`npm test`) must still pass.
- **Manual verification checkpoints** (real browser, user-performed, reported back — not a claimed-working tool): (1) Products page at a narrow resized width — confirm the Name column stays visible and correctly tinted while scrolling right, doesn't visually detach from the row; (2) Staff create/edit page at desktop vs. narrow width — confirm fields pair into 2 columns at desktop/tablet width and collapse cleanly to 1 column on mobile; (3) both focus-trapped panels (queue popover, customer-picker) — confirm `Tab`/`Shift+Tab` cycles only through the panel's own controls and doesn't escape to the page behind it, and that closing the panel returns focus to whatever opened it.

## Completion report

Same format and location as every prior phase (`docs/superpowers/plans/`): what was confirmed already-consistent (table scroll safety, form mobile-safety, Dashboard's existing responsive grid) vs. what was actually built (sticky-column pattern, `FormSection`, `useFocusTrap`), the manual verification results with the user's own reported observations quoted or summarized honestly, what's deferred to 38.4–38.6, and a final consistency-sweep note confirming no screen outside `ProductTable`'s and `StaffForm`'s pages was touched.
