# Phase 40.5 (Reports Creative Polish — New Charts) — Design

**Date:** 2026-08-03
**Status:** Approved by user, pending spec self-review
**Resolves:** the creative-polish half of TD-6's Reports module (per `docs/superpowers/specs/2026-08-02-phase-40-series-ui-ux-refinement-design.md`'s Phase 40.4/40.5 split — 40.4 shipped mechanical primitive adoption only; this phase adds the new visual content)

## Background

Phase 40.4 mechanically migrated all three Reports pages (Sales, Inventory, P&L) onto the shared design primitives. It shipped zero new visual content by design — the series spec deliberately isolated "primitive adoption" (40.4) from "creative polish + new charts" (this phase, 40.5) so a bad chart-design call wouldn't entangle with or block the mechanical rollout. Today, Sales/Inventory/P&L render only as stat tiles and tables; the only chart anywhere in the app is the Dashboard's `RevenueTrendChart.tsx`.

This phase's job, per the series spec: add real, working data visualizations to the three report pages, using the `dataviz` skill, constrained to the app's existing locked design tokens (no new palette).

## Scope decision, confirmed with the user directly

**This phase visualizes only data the report-building functions (`src/lib/reports/{sales,inventory,pnl}.ts`) already compute today — zero changes to those files, zero new aggregates.** A genuine time-series option (a day-by-day revenue trend within the selected date range) was considered and explicitly declined: it would require extending `buildSalesReport`/`buildPnLReport` with new aggregation logic in already-audited, already-shipped files, which is a real (if small) business-logic change — out of scope for a phase framed as visual/creative polish, not a data-model change. If a trend chart is wanted later, it's a legitimate future phase, not this one.

This decision has a clean downstream consequence: with no time-series chart in scope, **every chart in this phase is a "compare magnitude across categories" job** — per the `dataviz` skill's own choosing-a-form table, that means a single-hue **sequential** bar chart is the correct default everywhere, not a multi-hue categorical chart. This fits the app's deliberately small locked palette (`marine`/`brass`/`mist`/`slate`/`success`/`danger`/`warning`/`info` — confirmed by reading `globals.css` directly; no dark-mode variants exist, and no `tender-orange` token exists in code despite being named in `CLAUDE.md`) without needing to stretch it into a categorical set it was never designed for.

## Chart plan

| Report | New chart | Data source (already computed) | Form | Color |
|---|---|---|---|---|
| Sales | Revenue by branch | `report.byBranch` | Vertical bar | `marine` |
| Sales | Revenue by payment method | `report.byPaymentMethod` (3 fixed values: `cash`/`mtn_momo`/`orange_money`) | Vertical bar | `marine` |
| Sales | Top sellers | `report.topSellers`, capped to top 5 by the page's already-active sort | Horizontal bar | `marine` |
| Inventory | Stock value by branch | `report.byBranch` | Vertical bar | `marine` |
| P&L | Expenses by category | `report.expensesByCategory`, capped to top 5 | Horizontal bar | `brass` |

**Why `marine` for Sales/Inventory and `brass` for P&L's expense chart:** money/stock coming in or held (`marine`, matching `RevenueTrendChart.tsx`'s existing precedent exactly) versus money going out (`brass`, the app's own established secondary accent since the Phase 21/24 CECDE palette reconciliation) — a meaningful, tasteful distinction using only already-locked tokens, not a new color decision. `danger`/`success`/`warning` stay untouched and reserved for actual status (P&L's existing negative-net-income red stays exactly as it is today).

**Why capped to top 5:** `topSellers` and `expensesByCategory` are both unbounded in practice (product/service catalog size; free-text expense categories respectively). The `dataviz` skill is explicit that "more than ~7 classes that all carry meaning" belongs in a table, not a chart — and both datasets already have a complete, sortable table immediately below. The chart is a visual summary of the top 5, the table remains the full reference. `byBranch` and `byPaymentMethod` are not capped — branch count is small by this app's own architecture (single-location-to-multi-branch growth), and payment method is a fixed 3-value enum.

**P&L's three headline numbers (Revenue/Expenses/Net income) get no new chart.** Per `dataviz`'s own "is it even a chart?" table, "a handful of headline numbers" is correctly a KPI row of stat tiles — which Phase 40.4 already shipped via `Card`. Adding a redundant Revenue-vs-Expenses bar chart on top of that would visualize the same three numbers twice.

## Component architecture

Two new reusable client components in `src/components/reports/`, matching `RevenueTrendChart.tsx`'s existing established pattern (`'use client'`, `recharts`, hardcoded hex values matching the live CSS custom properties with the same documented "one deliberate exception to the zero-hardcoded-hex invariant" comment, `ResponsiveContainer`, a `Tooltip`):

- **`CategoryBarChart`** — vertical bars. Used for the three small-N magnitude-by-category cases: Sales' revenue-by-branch, revenue-by-payment-method, and Inventory's value-by-branch.
- **`RankedBarChart`** — horizontal bars, for legible long/variable-length labels. Used for the two "ranked, capped to top 5" cases: Sales' top sellers and P&L's expenses by category.

Shared prop shape for both: `{ data: { label: string; value: number }[]; color: string; valueLabel: string }`. Each report page maps its own already-computed aggregate into that shape inline with a one-line `.map()` (e.g. `report.byBranch.map(b => ({ label: b.branchName, value: b.revenue }))`) — no new shared data-transformation utility; each mapping is trivial enough that extracting one would be premature abstraction. `recharts` is already a project dependency (`package.json`) — no new package.

Both components run through the `dataviz` skill's mark specs (thin bars, rounded data-ends, recessive gridlines, selective direct labels rather than a number on every bar) and get a hover tooltip via recharts' `Tooltip`, matching `RevenueTrendChart`'s exact existing usage. `prefers-reduced-motion` handling will be confirmed against recharts' actual default transition behavior during implementation, not assumed — this app already handles reduced-motion globally in `globals.css` for its CSS-driven UI, and the implementation phase needs to confirm (not assume) that recharts' own internal transitions respect it, adding an explicit guard only if they don't.

## Placement

Each chart sits in its own `Card`-wrapped block, positioned after the existing stat-tile row and before its corresponding table section — charts are additions alongside the existing tables (which remain the complete, sortable, CSV-exportable reference), never replacements. Full page order:

- **Sales**: stat tiles → revenue-by-branch chart → revenue-by-payment-method chart → top-sellers chart → existing By-branch table → existing By-payment-method table → existing Top-sellers table (unchanged, including its sort-by-revenue/quantity links).
- **Inventory**: stat tile → value-by-branch chart → existing By-branch table → existing Stock-levels table (unchanged).
- **P&L**: stat tiles → expenses-by-category chart → existing Expenses-by-category table (unchanged).

## Validation & accessibility

Per the `dataviz` skill's non-negotiables:
- `scripts/validate_palette.js` will be run against `marine`/`brass` as the implementation's own verification step, not eyeballed — both are also independently used as this app's primary/secondary accent pair already, so a failure here would be a pre-existing issue, not one this phase introduces, but it gets checked regardless.
- Every chart is single-series, so no legend is needed (a single series needs no legend box — the chart title/section heading already names it, per `dataviz`'s own rule).
- A table view already exists for every chart (the existing tables below each one) — satisfying `dataviz`'s "a table view exists" accessibility requirement by construction, not as new work.
- No dark mode to validate against, since this app has none.

## Explicitly out of scope

- Any change to `src/lib/reports/{sales,inventory,pnl}.ts` or either report API route.
- A time-series/trend chart (declined above — would need new aggregation logic).
- Any change to the existing tables, CSV export, or capability checks.
- A new shared data-transformation utility (each mapping is inline and trivial).
- Dark-mode chart variants (app has no dark mode).
- Fixing `TD-8` (Button loading-state accessibility gap), `TD-4`/`TD-5`/`TD-7` (unrelated tech debt), or the `DownloadCsvButton` touch-target delta flagged in Phase 40.4's final review — all separately tracked, not this phase's job.
