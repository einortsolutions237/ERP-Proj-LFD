# Phase 38.2 — Motion & Feedback Foundation (Design)

## Purpose

The originally-pasted "Phase 38.2 / Premium UX, Motion & Interaction Polish" prompt spans roughly 9 largely independent UX concerns (micro-interactions/motion, loading/empty/error/success feedback, navigation, search, forms, table UX, mobile-prep cleanup, performance, plus a final consistency audit) — far more than any single phase in this project's 38-phase history has ever attempted at once. This is not a scope this phase absorbs whole; it's decomposed into a 4-phase sequence, agreed before any design work started:

- **Phase 38.2 (this phase)** — Motion & micro-interaction foundation, plus Error States and Success Feedback (grouped here because both are fundamentally about how an interaction communicates its outcome, the same territory as hover/focus/pressed/loading/disabled).
- **Phase 38.3** — The `Table` and `FormSection` primitives deferred from Phase 38.1, plus Loading States and Empty States (grouped with Table/FormSection because skeleton loaders and empty-state messaging are most concretely needed on the same table-heavy/form-heavy screen 38.3 builds against).
- **Phase 38.4** — Navigation & Search UX.
- **Phase 38.5** — Mobile-prep cleanup (removing fixed-width/flex blockers, explicitly NOT a responsive redesign), Performance (re-renders, layout shift, animation jank), and a final UI/UX Pro Max + Impeccable consistency audit closing out the whole initiative.

Each sub-phase gets its own brainstorm → spec → plan → execute → completion report, matching this project's established pattern (most recently Phase 38.1's own foundation-then-proof-screens shape).

Note on numbering: the pasted prompt's header said "Phase 38.2" but its body said "Phase 39 begins ONLY after Phase 38.1 is complete" — an internal inconsistency, almost certainly leftover template text. This phase is being tracked as **38.2** per the header, following directly from 38.1.

## Investigation findings (before any new work)

Direct inspection of the codebase, not assumption, found:

- **Duration is already 100% consistent app-wide**: every `duration-*` occurrence across the entire `src/` tree (150 occurrences across 78 files) is `duration-200`. Zero variance. No new token needed, no standardization work required — this is simply documented as a confirmed-clean finding.
- **Easing is already consistent**: zero explicit `ease-*` Tailwind classes exist anywhere in the codebase — every transition relies uniformly on Tailwind's default timing function. No change needed.
- **Reduced-motion is already handled globally**: `src/app/globals.css` already contains a `prefers-reduced-motion: reduce` media query that zeroes all transition/animation durations app-wide. Confirmed working, not a gap.
- **Pressed/active state is a genuine, total gap**: zero `active:` pseudo-class styling exists anywhere in the whole `src/` tree (a grep for `active:` matched only unrelated `isActive`/`active: boolean` business-logic field names, not CSS). This is real, concrete work.
- **Success feedback (toasts/confirmations) doesn't exist**: no toast/snackbar/confirmation component exists anywhere. `NotificationBell.tsx` is a different, pre-existing concept (persistent in-app notifications), not transient success feedback. This is genuinely new territory.
- **Error states are already reasonably solid** via the `Alert` primitive (built in Phase 38.1), but it currently lives on only 2 screens (Dashboard, POS/Checkout).

Because of these findings, this phase's real scope is narrower than the original prompt implied: mostly one concrete gap (pressed state) and one genuinely new primitive (toast), not an app-wide "standardize everything" effort.

## Scope shape

Same foundation-then-proof-screens shape as Phase 38.1: build/hardened primitives, prove them on a small, named set of screens, defer full app-wide rollout to later phases — consistent with `Button`/`Card`/`Badge`/`Alert`/`PageHeader`/`StatSummary` themselves still only living on 2 screens as of 38.1.

## 1. Pressed/active state (Button)

`src/components/ui/Button.tsx` gains an `active:` state per variant:
- A visibly deeper shade than the existing hover state (e.g. `primary`'s hover is `hover:bg-marine/90`; active becomes `active:bg-marine/80`), applied to every variant (`primary`, `secondary`, `ghost`, `danger`, `success`).
- A subtle tactile press effect, `active:scale-[0.98]`, via an added `transition-transform` alongside the existing `transition-colors` — small enough to read as "professional," not "bouncy." This automatically respects the existing global reduced-motion block (which zeroes transition *durations*, not the scale value itself — so the pressed state still visually registers instantly under reduced motion, it just doesn't animate into place).

No other primitive gets a pressed state in this phase — `Card` isn't used anywhere as a clickable/navigable element yet (its only interactive-adjacent behavior, `hoverable`, already exists from 38.1), so there's no real "press" interaction to design for until a future phase makes a Card clickable.

## 2. New primitive: Toast (success feedback)

- `ToastProvider` — a React Context, mounted once in `src/app/(dashboard)/layout.tsx` (the shared layout every authenticated screen already renders under). No new dependency — hand-built Context/state, consistent with this project's established caution about adding dependencies (Phase 35's own lesson).
- `useToast()` hook, exposing `showToast(message: string, tone?: 'success' | 'warning' | 'error' | 'info')` (tone defaults to `'success'`, matching the primary use case).
- The toast itself is a thin wrapper around the existing `Alert` component (boxed mode) — reusing `Alert`'s tone/color logic rather than duplicating it — plus: fixed positioning (bottom-right, stacked if more than one is active), an enter/exit transition (using the same `duration-200` convention already used everywhere), and auto-dismiss after ~4 seconds with a manual dismiss control. Uses `role="status"` for non-error tones and `role="alert"` for the `error` tone, matching `Alert`'s own accessibility pattern.

**Concrete wiring — POS/Checkout's sale-completion path** (`src/components/pos/CheckoutForm.tsx`): `showToast('Sale completed', 'success')` is called immediately before the existing `router.push(`/pos/sales/${body.id}`)` on a successful sale. This is deliberately verified to work correctly *because* `ToastProvider` lives at the shared layout level, which persists across this client-side route change — the toast is still visible on the receipt page after navigation, not lost mid-transition.

**Deliberately not wired to the offline-queue path** (the `queueOffline()` branch in the same file): a sale that gets queued for later sync already swaps in its own dedicated confirmation UI (`QueuedSaleReceipt`, from Phase 18.1) — a toast on top of an already-dedicated confirmation screen would be redundant, not additive.

## 3. Error-state hardening — Login as the second proof screen

Direct inspection of `src/app/login/page.tsx` confirms it currently has exactly the raw, pre-primitive shape 38.1 already solved elsewhere: a raw `<p role="alert" className="text-sm text-danger">` for its login-failure message, and a raw `<button>` with manual text-swap loading (`'Signing in…'` / `'Sign in'`). This phase migrates both onto the existing primitives:
- The error message → `<Alert tone="error" inline>`.
- The submit button → `<Button loading={submitting}>`.

No new `Alert` variant or tone is needed — its existing 4-tone set already covers every error category the original prompt describes (permission-denied, network, validation, offline are all representable as `tone="error"` with different copy; this phase doesn't invent a fifth "network" or "offline" tone).

## Out of scope for this phase (explicitly deferred)

- Loading states (skeletons/placeholders) and Empty states — Phase 38.3, alongside the `Table`/`FormSection` primitives they're most concretely needed for.
- Navigation, Search — Phase 38.4.
- Mobile-prep cleanup, Performance, final consistency audit — Phase 38.5.
- Any app-wide rollout of `Button`/`Card`/`Badge`/`Alert`/`PageHeader`/`StatSummary`/`Toast` beyond the 3 screens now touched across 38.1+38.2 (Dashboard, POS/Checkout, Login) — that's a standing, separate rollout effort, not folded into any of 38.2–38.5.
- No API, Firestore, permission, or Cloud Function changes anywhere, per every phase in this initiative.

## Verification

- Standard-desktop-viewport visual review via `claude-in-chrome` on POS/Checkout (pressed-state + toast) and Login (Alert/Button migration) — no `resize_window` use, consistent with the still-open, still-out-of-scope responsive-verification tool gap.
- Full existing test suite (`npm test`) must still pass.
