This held up under the final review's own independent re-checking.

The error-announcement scope area, however, was investigated by **enumerating a file list** rather than sweeping the whole `src/` tree programmatically — the same blind-spot class this project's own history already has a name for (Phase 33's `.where()`-shaped branch filter escaping its own grep sweep). This is recorded plainly rather than smoothed over, since accurately reporting a scoping miss is more valuable than a clean-sounding but incomplete result.

## What was built

### Contrast fix (Task 1)

**Files**: `src/app/globals.css`, `tests/unit/colorContrast.test.ts`
**Commit**: `5d0c5ee..5873f06`, task review clean (Approved, zero Critical/Important)

`--color-danger` changed from `#dc2626` to `#991b1b`. The old value passed against plain `paper` (4.62:1) but failed against its own `/10` badge-tint background — the tightest real case, used by 17+ files project-wide for voided/inactive/delete/low-stock pills and delete-button styling — computing to ≈4.13:1, below the 4.5:1 AA floor. The new value computes to ≈7.94:1 against plain paper and ≈6.95:1 against its own tint, both independently re-derived by two separate task reviewers and the final whole-branch reviewer (three independent computations, all agreeing to 3+ decimal places). A new test block was added mirroring the existing `success`/`warning` blocks exactly — reads the live token via `readCssToken`, never hardcodes an assumed-passing hex, and was confirmed to genuinely fail against the old value before the fix landed (a real revert-and-confirm-fail proof, per the exact lesson Phase 37's own review required). The final review additionally checked for reverse-contrast regression (darkening a color can hurt dark-on-dark pairings even as it helps light-on-dark) — every solid `bg-danger` usage in the codebase pairs with `text-paper`, which only improved (4.62:1 → 7.94:1); nothing regressed.

## The manual check — please run this and report back

This environment can verify that `role`/`aria-live` attributes are structurally present and correctly targeted in rendered JSX (via source read, computed contrast math, and the accessibility-tree structural facts a browser session can expose). It **cannot** verify that a real screen reader (VoiceOver/NVDA/JAWS) actually speaks these announcements, at what timing, or in what phrasing — the same tooling limit this phase named up front, the same shape as the `resize_window` gap. If you have access to a screen reader:

```
Phase 38.5 manual accessibility check — pick 2-3 of these (not all are
required, but each is a genuinely reachable trigger from this phase's own
changes, not pre-existing unmodified code):

1. Expenses (/expenses/new) — try to save with a required field missing or
   an invalid amount, confirm the screen reader announces the error
   automatically, without you needing to manually find it.
2. Payroll (/payroll/new) — same check, trigger its validation error.
3. Branches (add/edit a branch) — trigger its validation error.
4. Attendance widget (dashboard) — trigger a Check In or Check Out failure
   (e.g. by trying it twice in a row if that's rejected).
5. Seminars (create a seminar, or record attendance) — trigger a validation
   error on either form.
6. Reports (Sales or P&L) — pick an invalid date range and confirm the
   range error is announced.

Note: two fixes in this phase (Messaging's "contact not reachable" and
"can't reply" states in ThreadView.tsx) are structurally verified only —
they require a specific account/relationship state that isn't easy to
trigger on demand, so they're not included as testable steps here.

Report back: did the screen reader announce these automatically, or did
you have to manually find the error text yourself?
```
