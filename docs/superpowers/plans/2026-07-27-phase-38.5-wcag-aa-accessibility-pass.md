# Phase 38.5 — Full WCAG AA Accessibility Pass Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the real, evidence-backed accessibility gaps found by a full-codebase investigation — a systemic contrast failure on the `danger` token, two more instances of the exact form-id-uniqueness bug class Phase 38.4 found once, and 27 files whose error messages may or may not correctly announce to assistive tech — without touching business logic, capability gates, or the data model.

**Architecture:** This phase does not start from assumptions. A dedicated investigation (fork, full findings below) computed real WCAG contrast ratios from the actual token values in `globals.css`, grepped the entire `src/` tree for aria-label/landmark/form-id/error-announcement gaps, and tested what this environment can and cannot verify about real screen-reader behavior. Two of the brief's five scope areas (aria-label coverage, landmarks) came back clean — investigated, zero gaps, no task needed, reported honestly rather than padded with busywork. The other three produced real, scoped work: a one-token contrast fix that cascades correctly everywhere `danger` is used, a small defensive hardening matching Phase 38.4's own fix, and a per-file audit-and-fix-only-where-broken pass across 27 files.

**Tech Stack:** Next.js/TypeScript/Tailwind, no new dependencies. Contrast verification follows the exact WCAG relative-luminance methodology already established in `tests/unit/colorContrast.test.ts` (Phase 37) — read tokens from the live CSS file, compute contrast in code, never hardcode a target hex as "known passing."

## Investigation findings (grounding for this plan — read before executing)

**Tokens** (`src/app/globals.css`): ink `#0f172a`, paper `#f8fafc`, surface `#ffffff`, marine `#0f5c66`, brass `#c08a28`, mist `#e2e8f0`, slate `#475569`, success `#166534`, danger `#dc2626`, warning `#92400e`, info `#2563eb`.

**Contrast — one real, systemic failure found.** `danger` (`#dc2626`) passes against plain `paper` (4.62:1 — barely) but **fails against its own `/10` badge-tint background** (computed via this codebase's own established `blend(fg, bg, 0.1)`-over-`white` methodology from `colorContrast.test.ts`: ≈4.13:1, below the 4.5:1 AA floor) — success (5.86:1+) and warning (5.80:1+) both pass this same tightest-real-case check, confirmed in the same investigation; danger is the outlier because `#dc2626` is a brighter, lighter red than the dark green/amber used for the other two semantic tokens. `grep -rln "bg-danger/10" src/` returns **17 files** using this exact pattern (`Badge.tsx`, `Button.tsx`, `Alert.tsx`, and 14 screens' voided/inactive/delete/low-stock pills and delete-button styling) — this is the same class of gap Phase 31/37 already fixed for success/warning, never re-checked for danger. `brass` as text fails AA (2.91:1) but is used as real text nowhere — both occurrences (`DashboardCard.tsx:8`, `CheckoutForm.tsx:63`) are `aria-hidden` decorative icon glyphs, checked and confirmed not a defect. No hardcoded hex/rgb colors bypassing the token system were found anywhere in `src/` outside `globals.css` itself.

**aria-label coverage — investigated, zero gaps, no task needed.** `grep -rn "aria-label" src/ | wc -l` = 10 across 7 files, unchanged since Phase 38.3. Checked every icon-only `Button icon` call site (`CheckoutForm.tsx`'s quantity −/+/remove-line ×) — all already carry a real `aria-label`. Checked Phase 38.4's new mobile-card action buttons (Stock's Adjust/Transfer, Products' Edit/Delete, Sales Log's View) — all have clear visible text, correctly not flagged.

**Landmarks — investigated, zero gaps, no task needed.** Exactly two `<main>` elements in the whole codebase (`NavShell.tsx`, wrapping every dashboard page once; `login/page.tsx`, correctly outside `NavShell`) — no double-nesting anywhere. Two pages initially looked like they lacked a page-level `<h1>` (`messages/[peerUid]/page.tsx`, `seminars/[id]/page.tsx`) but both delegate to a client component that renders a real `<h1>` (`ThreadView.tsx:100`, `SeminarDetailClient.tsx:56`) — false positive, resolved by reading the delegate, not a gap.

**Form-label id-uniqueness — two more candidates found, same class as Phase 38.4's bug, neither currently exploitable.** `AttachScanForm.tsx:13` (`` `attach-scan-file-${labResultId}` ``) and `LeaveReviewButtons.tsx:71,75` (`` `leave-review-note-${requestId}` ``) both derive field ids from a prop value rather than `useId()` — the exact shape that broke Stock's forms once a mobile/desktop dual-render existed. Neither is currently rendered twice simultaneously anywhere in the codebase, so neither is live-broken today. Sampled 10+ other form-bearing files across Customers/Suppliers/Departments/Staff/Seminars/Appointments/Treatments/Lab/Questionnaire/Leave — no other instance found.

**Error announcement — the largest real gap.** `Alert`'s `role`/implicit-`aria-live` behavior (Phase 38.2) is used in only ~7 files. **28 files still render a raw, non-`Alert` error message** (the investigation's own summary said "27" — recounting its enumerated list directly gives 28; corrected here rather than repeated): `AppointmentForm.tsx`, `AppointmentsTable.tsx`, `AttachScanForm.tsx`, `DemographicsForm.tsx`, `LabOrderForm.tsx`, `LabResultForm.tsx`, `NursingVisitForm.tsx`, `QuestionnaireEditor.tsx`, `TreatmentForm.tsx`, `CustomerForm.tsx`, `DeleteCustomerButton.tsx`, `DepartmentForm.tsx`, `DepartmentTable.tsx`, `LeaveRequestForm.tsx`, `LeaveReviewButtons.tsx`, `ThreadView.tsx`, `PendingDeliveriesSection.tsx`, `VoidSaleButton.tsx`, `ProductForm.tsx`, `ProductTable.tsx`, `RoleReassignmentTable.tsx`, `ServiceForm.tsx`, `ServiceTable.tsx`, `StaffTable.tsx`, `StockAdjustForm.tsx`, `StockTransferForm.tsx`, `SupplierForm.tsx`, `SupplierTable.tsx`. Whether each already has a correct `role="alert"` (just not via the shared component) or is genuinely missing one was explicitly **not** assumed by the investigation — it needs a real per-file check. `useToast`/`ToastProvider` confirmed used in exactly 2 files (`CheckoutForm.tsx`, `ToastProvider.tsx` itself) — nowhere else, as suspected, not a gap to fix.

**Tooling limits, stated up front (the `resize_window` lesson applied here).** This environment can verify that `role`, `aria-live`, and `aria-label` attributes are structurally present and correctly targeted in rendered JSX/DOM — via source read, computed contrast math, and (when a browser session connects) reading the accessibility tree. It **cannot** verify that a real screen reader (VoiceOver/NVDA/JAWS) actually speaks an announcement, at what timing, or in what phrasing — no tool available here drives real assistive-tech software. `claude-in-chrome`'s accessibility-tree read would at best confirm the same structural facts already checkable from source, not real synthesized speech or timing — and this project's own history (Phases 21/22/23/26/26.1) shows that even that structural browser cross-check isn't reliably connectable session-to-session. This is the identical shape to the `resize_window` gap: a genuine, separate, human-only verification step, named here at the start rather than discovered at the end. Task 5 below turns this into an explicit, concrete manual-check request, delivered the same way Phase 38.4's mobile checklist was.

## Global Constraints

- No business logic, capability gating, schema, or data-model change anywhere in this phase.
- No new UI primitives — `Alert` already exists and already does everything this phase's error-announcement fixes need; use it or a plain `role="alert"` addition, never build a parallel mechanism.
- Contrast verification must compute ratios from the live token value in `globals.css` (via `readCssToken`, already established in `colorContrast.test.ts`), never hardcode an assumed-passing hex as a test target — this is a direct, named lesson from Phase 37's own regression-test mistake.
- No `resize_window`, no simulated screen-reader dependency anywhere in this phase's own verification — every task verifies structurally (source read, computed contrast, `tsc`/`build`/`test`). Task 5 delivers the real, human/AT-verification checklist as a concrete deliverable in the chat response, not just filed in the completion report.
- Aria-label and landmark scope items are **investigated, not tasked** — zero gaps were found, and the plan does not manufacture busywork to look thorough. If a task's own execution surfaces a real gap in either area, treat it as a genuine finding and fix it, flagged in that task's report.
- Every task's review is Sonnet-tier — this phase is styling/markup/accessibility-attribute work with zero transaction or business-logic changes, matching the precedent set by every prior 38.x task.

### Task 1: Fix the `danger` token's contrast failure against its own `/10` badge tint

**Files:**
- Modify: `src/app/globals.css`
- Modify: `tests/unit/colorContrast.test.ts`

**Interfaces:** None new. `--color-danger` is consumed everywhere via Tailwind's generated `text-danger`/`bg-danger/10`/`border-danger` utilities — changing the token's value cascades correctly to all 17 files using the pattern without touching any of them individually.

- [ ] **Step 1: Write the failing test first**

In `tests/unit/colorContrast.test.ts`, add a new `describe` block mirroring the existing `success`/`warning` blocks exactly (same `PAPER`/`WHITE` constants, same `blend`/`contrastRatio` helpers already in the file — do not duplicate them):

```ts
const DANGER = readCssToken('color-danger')

describe('danger token contrast (WCAG AA, 4.5:1)', () => {
  it('danger text passes against the app paper background', () => {
    expect(contrastRatio(DANGER, PAPER)).toBeGreaterThanOrEqual(4.5)
  })
  it('danger text passes against its own /10 badge background (tightest real case)', () => {
    expect(contrastRatio(DANGER, blend(DANGER, WHITE, 0.1))).toBeGreaterThanOrEqual(4.5)
  })
})
```

- [ ] **Step 2: Run the test to confirm it fails against the current token**

Run: `npm test -- tests/unit/colorContrast.test.ts`
Expected: the new "against its own /10 badge background" assertion FAILS (current `#dc2626` computes to ≈4.13:1, below 4.5) — this is the real, honest revert-and-confirm-fail proof Phase 37's own review required for its contrast fix; do not skip straight to applying the fix.

- [ ] **Step 3: Apply the fix**

In `src/app/globals.css`, replace:

```css
  --color-danger: #dc2626;
```

with:

```css
  --color-danger: #991b1b;
```

`#991b1b` was computed in this plan's own investigation: **7.94:1 against plain paper**, **6.95:1 against its own `/10` badge tint** (both comfortably clear 4.5:1, in the same dark-saturated-hue family as `success`/`warning` rather than danger's previous comparatively bright red). Show your own arithmetic in the task report rather than trusting this plan's numbers blindly — re-derive both ratios independently using the test file's own `relativeLuminance`/`contrastRatio`/`blend` functions before claiming this step done.

- [ ] **Step 4: Run the test again to confirm it passes**

Run: `npm test -- tests/unit/colorContrast.test.ts`
Expected: all 6 assertions (2 existing success/warning blocks + the new danger block) PASS.

- [ ] **Step 5: Visual/structural scope check**

Confirm via `grep -rln "bg-danger/10\|text-danger\|border-danger" src/` that no file needed a direct edit — the fix is entirely in `globals.css`. Run `npx tsc --noEmit` and `npm run build` to confirm nothing else broke (Tailwind regenerates its utility classes from the token automatically; a color value change alone cannot introduce a type error, but confirm anyway per this project's standing practice of never trusting "should be fine").

- [ ] **Step 6: Commit**


### Task 3: Error-announcement audit and fix — batch A (clinical, HR, messaging)

**Files to check** (confirm each real path by reading the file — do not guess directory structure):
`AppointmentForm.tsx`, `AppointmentsTable.tsx`, `AttachScanForm.tsx`, `DemographicsForm.tsx`, `LabOrderForm.tsx`, `LabResultForm.tsx`, `NursingVisitForm.tsx`, `QuestionnaireEditor.tsx`, `TreatmentForm.tsx`, `LeaveRequestForm.tsx`, `LeaveReviewButtons.tsx`, `ThreadView.tsx`

**Interfaces:** None new. `Alert` (`src/components/ui/Alert.tsx`) already exists: `<Alert tone="error" inline>{message}</Alert>` renders `role="alert"` with implicit `aria-live="assertive"` per the ARIA spec — this is the reference behavior every file below is checked against.

**Note**: `AttachScanForm.tsx` and `LeaveReviewButtons.tsx` will already have Task 2's `useId()` change applied before this task starts — check their error-rendering on top of that state, not the pre-Task-2 version.

- [ ] **Step 1: For each of the 12 files above, do exactly this check-then-fix**

For each file:
1. Find where it renders a validation/error message to the user (grep the file for `role="alert"`, `text-danger`, or wherever an error string is conditionally rendered).
2. **If it already has `role="alert"` (or `role="status"` for a non-error confirmation) directly on the element that actually contains the error text** — this file is already correct. Do nothing to it. Note this in your report as "checked, already correct, file:line."
3. **If the error is rendered with no `role` at all** (a plain `<p className="text-danger">{error}</p>` or equivalent, with nothing announcing it to assistive tech) — this is a real gap. Fix it the simplest correct way: if replacing the plain element with `<Alert tone="error" inline>{error}</Alert>` is a clean drop-in (same conditional, same message variable, no layout disruption), do that. If the surrounding markup makes a full `Alert` swap awkward, adding `role="alert"` directly to the existing element is an acceptable minimal fix — but prefer `Alert` where it's a clean fit, since building the same `role`/`aria-live` logic by hand anywhere `Alert` already exists is reinventing what the shared component already does correctly.
4. Do not migrate a file's error markup onto `Alert` purely for visual consistency if it already has a correct `role` — that's Phase 38.6's territory (final cross-skill consistency audit), not this phase's accessibility scope. Only fix what's actually missing the announcement mechanism.
