## Declined: a shared responsive-table primitive

Recorded in the plan's Global Constraints before implementation began, and re-examined by the final whole-branch review once all three tables existed side by side: three tables (Stock, Products, Sales Log) now need the identical "cards below `md`, table at `md:` and up" structural split, which could look like it finally justifies a shared component. The decision held — Stock's two expandable stateful forms are genuinely unlike Products' two action links or Sales Log's one view link, and render-prop plumbing for that difference would have cost more than the duplication. The final review's honest caveat, worth carrying forward: the duplication did produce three small drift instances within this one phase (missing `shrink-0`/`truncate` in two places, one mismatched tooltip — see Minor findings below), a faster drift rate than "worth it only if a fourth table ever needs this" assumed. If a fourth table needs this treatment, extract a shared card shell + empty-state pattern at that point — not a full table abstraction.

## Final whole-branch review (Opus): Ready to merge — With fixes, now applied and re-verified

**Range reviewed**: `9fa5f66..f4c3931` (all 4 tasks together, checking cross-task consistency a per-task review can't see)

**Important #1 (fixed)**: the mobile card and desktop table both mount `StockAdjustForm`/`StockTransferForm` simultaneously whenever a row's form is open (one CSS-hidden, not unmounted) — a genuine architectural consequence of the card/table split this phase introduced. Both forms derived their field `id`s from `productId` alone, which was unique before this phase (only one instance ever existed) but no longer is. Per the HTML spec, `<label for="x">` resolves to the *first* DOM element with that id — since the mobile block renders before the desktop block, every label in these two forms was pointing at the hidden mobile input, breaking desktop label-click-to-focus and screen-reader label association. **Fixed** (commit `f4c3931..d83b49d`): both forms now derive their field ids from React's `useId()` instead of `productId` — unique per component instance, SSR/hydration-safe, and more correct in general than relying on prop-value uniqueness. Re-review confirmed every `productId`-based id string is gone from both files and every `htmlFor`/`id` pair still resolves correctly.

**Important #2 (recorded as a known limitation, not fixed — explicit human-partner decision)**: because the mobile card and desktop table are two independent component instances with independent `useState`, a user who starts filling in Stock's Adjust or Transfer form and then resizes the window across the `md` breakpoint mid-edit will see their input silently reset — inherent to the CSS-only split, not a bug introduced carelessly. A low-cost mitigation (lifting form field state into `StockTable` alongside `openForm`) exists but was judged not worth the added complexity for a UI-only phase, given real-world risk is low (resizing mid-form-fill on the same device is a narrow edge case). **This is the one open, deliberately-accepted limitation from this phase** — worth a real fix if it's ever reported as an actual user complaint, not before.

**Minor findings, fixed alongside #1** (commit `f4c3931..d83b49d`): Stock's mobile "Low stock"/"OK" badges and Sales Log's "Voided" badge were missing `shrink-0` (present on Products' equivalent pills, absent here — textbook copy-paste drift, the exact risk the declined-primitive section above names); Stock's mobile SKU+branch line was missing `truncate` (present on Products'/Sales Log's equivalent secondary lines). Both fixed, both re-verified.

**Minor findings, parked (recommendations for a future phase, not blocking)**: Stock's mobile Adjust/Transfer buttons use the `Button` primitive while the desktop table keeps raw markup for the same buttons — a real inconsistency in applying the plan's own "match byte-for-byte or use raw markup" rule, but in the direction of the primitive being arguably better, not worse; Products' mobile secondary-line `title` tooltip covers only half its visible text (cosmetic); the three mobile card lists use `<div>` rather than `<ul>/<li>` (consistent across all three, not drift, but real list semantics would help screen readers); DOM-doubling at every viewport width is the standard cost of a CSS-only responsive split, worth revisiting toward a JS-media-query or shared-primitive approach only if a table grows to a few hundred rows.
