## Step 2 — Production build output

```bash

```

Result: **build succeeded cleanly** (`✓ Compiled successfully in 4.9s`, TypeScript finished in 5.9s, all 85 static-generation workers succeeded).

Confirmed exactly as expected: the route table prints only `○`/`ƒ` markers, **no per-route "First Load JS" size column**. Out of the full route list, only `/login` and `/_not-found` are `○` (static); every other route — including `/stock`, `/products`, and `/pos/sales` (the Sales Log) — is `ƒ` (dynamic/server-rendered), gated by the session-cookie check in a Server Component. This is a real tooling limitation of Next.js's build summary, not a bug in this app: the summary only computes First Load JS for statically-analyzable routes, and this app is almost entirely dynamic by deliberate design (the login-gate architecture predates this phase). Named plainly here rather than fabricating a number the build output doesn't provide — same posture already established in this project for the `resize_window` tool gap (Phases 24/36/38) and the screen-reader verification gap (Phase 38.5).

### Cross-reference against source size

Source line counts for the three components responsible for the mobile-card + desktop-table split (Phase 38.4):

| Component | Lines | Route chunk |
|---|---|---|
| `src/components/stock/StockTable.tsx` | 284 | 15,143 bytes |
| `src/components/products/ProductTable.tsx` | 184 | 6,297 bytes |
| `src/components/pos/SalesTable.tsx` | 128 | 4,828 bytes |

The ordering of compiled chunk size (Stock > Products > Sales Log) tracks directly with the ordering of source-file size, which in turn tracks with each component's actual feature complexity — not with the mobile/desktop duplication itself. `StockTable.tsx` is the largest of the three specifically because, as already documented in this project's own history (Phase 38.4), it carries **two stateful, expandable forms per row** (Adjust and Transfer, both now mounted twice — once per breakpoint, via `useId()`-differentiated instances) — a materially different and heavier row shape than `ProductTable.tsx`'s two links or `SalesTable.tsx`'s one link. Stock being the largest route chunk among these three is therefore explained by its pre-existing form complexity, the same reason already on record for why a shared responsive-table primitive was declined in Phase 38.4 — not by any newly-discovered bloat specific to the doubling pattern.

No component surfaced as unexpectedly or disproportionately large relative to its own source size or feature set. Nothing here rises to a separate follow-up.

## Step 3 — Conclusion

Current live data volumes (5 products, 1 service, 7 productStock docs, 26 sales, 61 stockMovements, 2 branches, 9 customers) remain far below Phase 38.4's own stated revisit threshold of "a few hundred rows." At these volumes, rendering both a mobile card list and a desktop table for the same row set (currently at most 7-26 rows per screen, depending on the collection) produces a trivial amount of extra DOM — not a measurable rendering-performance concern by any realistic metric, and nothing a user would perceive.

The compiled chunk sizes for `StockTable.tsx`/`ProductTable.tsx`/`SalesTable.tsx`'s route chunks are unremarkable: they scale with each component's own source complexity, not with anything unique to the card+table duplication, and none of the three appears as an outlier against the rest of the app's ~54 route chunks (the two genuinely large outliers — `customers/[id]` and `/pos` — are unrelated screens with their own, larger feature sets).

**No code change is being made as a result of this task.** Per the phase brief's own explicit permission: the DOM-doubling pattern introduced in Phase 38.4 is confirmed not to be a real performance concern at current or realistic near-future scale, and this finding is being stated plainly rather than manufacturing a fix for a problem the measurements don't show.

## Step 2 tooling-limitation note (restated for the record)

Next.js's production build summary cannot report First Load JS for this app's routes because nearly every route is `ƒ` (dynamic, server-rendered, gated by a session-cookie check) rather than `○` (statically analyzable). This is architectural, not a defect introduced by this phase or any prior one, and is named here in the same spirit as this project's other two acknowledged, unresolved tooling gaps: `resize_window` reporting success without actually changing the viewport (Phases 24, 36, 38), and the inability to verify real screen-reader announcement behavior in this environment (Phase 38.5). Compiled chunk size was used as the best available concrete substitute measurement for this task.
