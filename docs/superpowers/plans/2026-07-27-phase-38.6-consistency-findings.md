# Phase 38.6 — Final cross-initiative design-consistency audit

**Method: DEGRADED — single-context, code-level critique only.**

Two things this run could not do, both stated plainly rather than papered over:

1. **No sub-agent orchestration.** The task brief for this run explicitly instructed "do not spawn further subagents — perform the critique yourself, directly," which overrides the `impeccable:impeccable` `critique` command's own hard invariant of running Assessment A (design review) and Assessment B (detector + browser evidence) as two isolated sub-agents. This is a deliberate, instructed degradation, not an oversight — the `impeccable` skill's own protocol requires this banner whenever that happens.
2. **No live browser session.** No `next dev` server was running in this environment (`netstat -ano | findstr :3000` returned nothing before this audit started), and none was started for it. Per this task's own instructions, a code-level critique — reading the actual rendered JSX/className usage across the target screens' source files, and cross-referencing which of the seven primitives (`Button`, `Card`, `Badge`, `Alert`, `PageHeader`, `StatSummary`, `FormSection`) each screen does or doesn't use — is the accepted, honest substitute. That is what this document is. No visual screenshot, real contrast measurement, or interaction test was performed; every claim below is a direct read of source, not an inference.

This also means Assessment B's detector (`detect.mjs`, tuned for marketing/AI-slop tells — gradient text, eyebrow kickers, hero-metric templates) was not run. It is a poor fit for this specific, narrower task anyway (a cross-screen primitive-consistency check, not a from-scratch slop audit of a product register app), so its absence does not weaken this particular finding set the way it would for a general `critique`.

## Step 1 — Core initiative screens (Dashboard, POS/Checkout, Stock, Products, Sales Log, Login)

These are the six screens that went through real primitive/responsive/accessibility work across Phases 38.1–38.5. The check here is the same one Phase 10 established as good practice: drift *between* independently-styled screens, not just within each one.

**Overall: consistent, with one real and now-fixed exception.** Dashboard, POS/Checkout (`pos/page.tsx`), and Login all use `PageHeader`/`Alert`/`Button` correctly and identically in shape. The one recurring drift found was specific and mechanical: **a component's own desktop-table code path hand-rolling a badge or button that an adjacent code path in the very same file (its own mobile-card view, or its own imports) already built with the real primitive.** This is exactly the kind of "drift between independently-styled screens" Phase 10 flagged as worth catching, just one level down — drift between two render paths of the same component instead of between two screens.

### Findings — fixed this phase (classification (a): pure mechanical swap, same class strings, same tokens, zero color/font/business-logic changes)

| # | File | Issue | Fix |
|---|------|-------|-----|

| 2 | `src/app/(dashboard)/pos/sales/page.tsx` | Raw `<h1 className="font-display text-xl font-semibold text-ink">Sales log</h1>` instead of `PageHeader` (size happened to already match `PageHeader`, but the primitive itself was never called) | Replaced with `<PageHeader title="Sales log" />` |

| 4 | `src/components/stock/StockTable.tsx` | Desktop Adjust/Transfer actions were raw `<button>`s manually styled to approximate `Button`'s `secondary` variant, while the same file's mobile-card view for the identical actions already calls `<Button variant="secondary">` | Desktop actions now call `<Button variant="secondary">`, matching the mobile view |
| 5 | `src/components/stock/StockAdjustForm.tsx` | Inline error was a raw `<p role="alert" className="text-sm text-danger">` — byte-identical to `Alert`'s own `inline` + `tone="error"` + default `size="sm"` output (`text-sm text-danger`, same `role="alert"`). Delivery status now `<Badge tone={DELIVERY_STATUS_TONE[d.status] ?? 'neutral'}>{d.status}</Badge>` with a small `pending→warning / fulfilled→success` tone map replacing the class-string dict; `pendingDeliveries[].status` is a closed two-value enum in this codebase, so the `?? 'neutral'` fallback is unreachable in practice, not a live behavior change |

All eight fixes verified: `npx tsc --noEmit` on the full project is clean after the edits; `npx vitest run` shows 431 passed / 0 failed on every test that can run without the Firestore emulator (which is not running in this environment — the 89 "skipped" integration tests fail only with `ECONNREFUSED 127.0.0.1:8080`, unrelated to these UI-only edits and present identically before this phase's changes).

### Findings — real, but not fixed this phase (classification (b): out of scope for a same-day mechanical fix)

- **`src/components/products/ProductTable.tsx`** has the identical class of gap as `StockTable.tsx` did (active/inactive status pills and Edit/Delete row actions are all raw `<span>`/`<Link>`/`<button>` markup, in both its mobile-card and desktop-table views — it doesn't import `Badge` or `Button` at all), but it is **not** a clean one-for-one swap the way `StockTable.tsx` was: the "active" pill (`bg-success/10 text-success`) is byte-identical to `Badge tone="success"`, but the "inactive" pill uses `bg-slate/10 text-slate`, which does **not** match `Badge`'s `neutral` tone (`bg-mist text-slate`) — swapping it in would be a small but real visual color change, not a pure mechanical one. Since half the pair can't be swapped safely, this file was left as-is rather than partially migrated. **Not added to CLAUDE.md as its own backlog item** — it's the same underlying gap as the broader Step 2 finding below (primitives not yet extended past the six core screens), just noted here for precision since `ProductTable.tsx` is nominally a "core" file.
- **`src/app/(dashboard)/pos/sales/[id]/page.tsx`**'s own top-level `<h1 className="font-display text-2xl font-semibold text-ink">Sale detail</h1>` is also not on `PageHeader`, but unlike the two page-header fixes above, this page's header row has a description line, a conditional void-status block, and a `PrintReceiptButton` positioned as a true header action — collapsing it onto `PageHeader` would require restructuring the conditional void/description content into the `description` slot, which crosses into "restructuring," explicitly out of this task's mechanical-fix bar. Left as a documented gap, not fixed.

## Step 2 — Screens outside this initiative's direct scope

Covered: Roles, Seminars (list + detail), the clinical-record sections of the customer detail page (`ClinicalSection.tsx`, and by extension `IntakeSection.tsx`/`LabSection.tsx`), Messaging, Accounting (Expenses, P&L), Payroll, and the four Reports pages (Sales/Inventory/P&L — Expenses has no separate `/reports/expenses` route; its own list page at `/expenses` is the only "expenses report" view that exists, confirmed by directory listing).

**This is a real, visible gap between the refined core and everything else — confirmed by direct file reads, not assumption.** Every one of the following files was opened and grepped for `@/components/ui/*` imports:

- `src/app/(dashboard)/roles/page.tsx`, `src/components/roles/RoleMatrix.tsx`, `RoleReassignmentTable.tsx`
- `src/app/(dashboard)/seminars/page.tsx`, `seminars/new/page.tsx`, `seminars/[id]/page.tsx`, `src/components/seminars/AttendanceTable.tsx`, `SeminarDetailClient.tsx`
- `src/components/clinical/ClinicalSection.tsx`, `IntakeSection.tsx`, `LabSection.tsx`, `TreatmentForm.tsx`, `LabOrderForm.tsx`, `LabResultForm.tsx`
- `src/app/(dashboard)/messages/page.tsx`, `messages/[peerUid]/page.tsx`, `src/components/messaging/ConversationList.tsx`
- `src/app/(dashboard)/expenses/page.tsx`, `payroll/page.tsx`
- `src/app/(dashboard)/reports/sales/page.tsx`, `reports/inventory/page.tsx`, `reports/pnl/page.tsx`

None of these import `Button`, `Card`, `Badge`, `PageHeader`, `StatSummary`, or `FormSection`. Every one of them still uses the pre-38.1 raw-Tailwind pattern throughout: a raw `<h1 className="font-display text-2xl font-semibold text-ink">` (or `text-xl`, inconsistently — the two sizes are mixed across these files exactly the way they were in Stock/Sales Log before this phase's fix, just not fixed here since these files are out of this initiative's scope), raw `rounded-2xl border border-mist bg-surface ... shadow-[var(--shadow-card)]` divs standing in for `Card`, raw stat tiles standing in for `StatSummary` (see `reports/sales/page.tsx` and `reports/pnl/page.tsx`, each with 3–5 hand-rolled `rounded-2xl border ... p-3` stat divs), and raw `<button>`/styled `<Link>` standing in for `Button`.

**One partial, genuinely positive exception, worth naming precisely**: `Alert` — and only `Alert` — has propagated into several of these files (`SeminarForm.tsx`, `AttendanceForm.tsx`, `ThreadView.tsx`, `BranchForm.tsx`, `SettingsTable.tsx`). This lines up exactly with CLAUDE.md's own record of Phase 38.5's error-announcement sweep, which mechanically added `Alert`-based announcements across Accounting/Payroll/Branches/Attendance/Seminars/Settings/Reports — a different, narrower, already-completed piece of work than the primitive-rollout this task is checking for. So the gap is real but not total: one of the seven primitives is everywhere; the other six are confined to the six core screens (plus `StaffForm.tsx`, which also has `FormSection`/`Button` from Phase 38.3).

**This is real, and it is not a one-line fix.** Extending `Button`/`Card`/`Badge`/`PageHeader`/`StatSummary`/`FormSection` across Roles, Seminars, Clinical, Messaging, Accounting, Payroll, and all four Reports pages touches dozens of files across seven modules that were never in scope for any prior design-rollout phase (Phase 34's "Roles module fully migrated" was a color/contrast-token fix — tinted-badge checkmarks replacing raw colored text — not a primitive-component migration; it does not conflict with this finding, it's a different axis of "migrated"). Per this task's own brief, that is out of scope for this same-day fix and is **not** silently expanded into a new design-rollout project here. It is recorded below as an explicit new CLAUDE.md backlog item instead.

**Reports pages specifically** also repeat the same raw stat-card and raw `<table>` markup nearly verbatim across all three files (`reports/sales`, `reports/inventory`, `reports/pnl`) — this is the same *kind* of repeated-but-not-shared pattern Phase 38.4 already considered and declined to extract for the three responsive tables (Stock/Products/Sales Log), for the same reason (each report's actual data shape differs enough that a shared abstraction wasn't judged worth the plumbing). Per this task's instructions, that tradeoff is treated as already-accepted, not re-litigated or proposed as a new abstraction here — only flagged because it's directly relevant to the consistency question this audit was asked.
