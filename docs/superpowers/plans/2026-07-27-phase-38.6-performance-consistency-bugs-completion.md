## Section B — Tasks 3-6: Three confirmed bug fixes

### Task 3: `super_admin` role-edit guard — check the actor, not just the target

**Files**: `src/app/api/staff/[staffId]/route.ts`, `tests/integration/staffRoleEdit.test.ts` (new), `CLAUDE.md`
**Commits**: `18a0604` (base fix), `e37dac7` (self-edit fix added after Opus-tier review)

Confirmed by direct read: `PATCH /api/staff/[staffId]`'s super_admin-protection guard checked only `existing.role === 'super_admin'` (the *target*), never the *actor's* role — unconditionally blocking role/status changes to any super_admin-tagged account, including by another super_admin. Fixed to `existing.role === 'super_admin' && user.role !== 'super_admin'`, then — after this task's own Opus-tier review flagged a self-approval gap — tightened further so a super_admin actor still cannot demote or deactivate **themselves**, matching the same self-action-prevention shape already used by leave-request self-approval. `CLAUDE.md`'s Permissions paragraph was updated in the same task to describe this precisely.

### Task 6 (added mid-execution): `StaffForm.tsx` UI gate

**Files**: `src/app/(dashboard)/staff/[staffId]/page.tsx`, `src/components/staff/StaffForm.tsx`
**Commit**: `239f2aa`

Task 3's own review found the server-side fix alone left the originally-reported bug unreachable through the actual UI — `StaffForm.tsx` unconditionally disabled the role/status fields whenever the target was super_admin-tagged, with no check on who was acting. Fixed: the edit page now passes `viewerRole`/`viewerUid` down; the role `<select>` is enabled (with `super_admin` added as a real, pre-selected `<option>` to prevent a silent accidental demotion) and the status `<select>` is enabled, in exactly the one case where a super_admin actor edits a *different* super_admin and is not self-editing.

## Final whole-branch review: findings and this fix wave

The final whole-branch review (covering the complete diff across all 6 tasks, `d0a37a8..57769a9`) confirmed Task 3/Task 6's server-and-UI gating match exactly (no combination where the UI allows an edit the server would reject, or vice versa), Tasks 1/2/4 made no unlogged application-code changes, and Task 5's two pages match the existing CSV pattern structurally. It also caught three things no individual task's own review had caught, all fixed in this single wave:

1. **Real bug — `attemptsDeactivate` fired on an unchanged value, not an actual transition.** `src/app/api/staff/[staffId]/route.ts:38` read `body.employment?.status === 'inactive'` with no comparison against the target's *current* status — so once any super_admin was ever deactivated (now possible after Task 3), every subsequent edit to that account by anyone (even an unrelated field change) would incorrectly re-trip the guard, because the disabled/protected form field always resubmits the already-current status. Fixed to require an actual transition, matching the exact pattern already used two lines below for `statusChangedToInactive`: `body.employment?.status === 'inactive' && existing.employment?.status !== 'inactive'`.

2. **Real bug — the disabled status label could display false information.** `src/components/staff/StaffForm.tsx:302` hardcoded `value="active (protected — cannot be deactivated here)"` regardless of the target's real current status, which — after Task 3/6 — can now genuinely be `'inactive'` for a super_admin. Fixed to `value={\`${status} (protected — cannot be changed here)\`}`, matching the exact phrasing style already used by the role field's own protected label a few lines above, and covering both directions (active→protected, inactive→protected) rather than assuming only one.

3. **Doc reconciliation gap** — Tasks 1-6 each edited `CLAUDE.md` independently across their own commits, and nobody reconciled the result into one coherent narrative. Fixed: inserted a single consolidated Phase 38.6 paragraph in the `## How` section covering the bug-fix half of the phase (naming the accepted demote-then-delete second-order consequence explicitly — see below), removed the now-stale "Not yet planned... Phase 38.6" line, retitled "Separately tracked, from Maxim directly" (dropping "still awaiting information," no longer accurate now that 3 of 4 items are resolved), and rewrote items 1, 3, and the summary paragraph below the numbered list to say RESOLVED rather than still-open.

A fourth item, **not a bug fix but a real, accepted second-order consequence**, was named explicitly (both in this report and in the new CLAUDE.md paragraph) rather than left implicit: because `DELETE /api/staff/[staffId]`'s own guard is unchanged and still checks only the target's *current* role, a super_admin can now demote a different super_admin (via the newly-fixed PATCH path) and then delete them — a two-step full removal of another super_admin that Task 3's own scope never explicitly decided on. Traced and confirmed safe as an invariant: since self-edit is always blocked, this can never reduce the organization to zero super_admins — only ever down to exactly one, since removing anyone else always requires a different, still-standing super_admin to act. Accepted as an intended property of "super_admins govern each other," not fixed further, per direct instruction.

Also **added, not caught by the final review but a natural completion of Task 2's own finding**: TD-6 in `docs/tech-debt.md`, formalizing the design-rollout backlog item (Roles/Seminars/clinical sections/Messaging/Accounting/Payroll/Reports still on raw Tailwind) as a tracked tech-debt entry rather than only a CLAUDE.md mention.

**Phase 38.5's screen-reader manual-verification gap remains open** — unchanged by this fix wave, not silently dropped from tracking.
