## The 6 UI primitives (Tasks 2–7)

### Button (Task 2)

**File**: `src/components/ui/Button.tsx`

**API**: `variant?: 'primary' | 'secondary' | 'ghost' | 'danger' | 'success'` (default `primary`), `icon?: boolean` (square icon-only sizing), `loading?: boolean` (swaps children for a spinner, ORs into `disabled`), extends `ButtonHTMLAttributes<HTMLButtonElement>`.

`type` defaults to `'button'` and is destructured out of the JSX spread (`...rest`) before it's applied — spreading `{...rest}` after an inline `type={type}` attribute would silently reset it to the HTML default (`type="submit"`) whenever a caller doesn't pass `type` explicitly, since `rest` would still contain an `undefined` `type` key. Reviewer independently confirmed this ordering is correct in the shipped code.

### Card (Task 3)

**File**: `src/components/ui/Card.tsx`

**API**: `variant?: 'default' | 'nested'` (default `default`), `hoverable?: boolean` (adds `hover:shadow-[var(--shadow-card-hover)]`), extends `HTMLAttributes<HTMLDivElement>`.

Deliberately has **no `bg-*` class of its own** — background is always supplied by the caller via `className`, documented inline as a comment explaining why: Tailwind's generated stylesheet orders same-specificity utilities by its own internal rule order, not by className string order, so two competing `bg-*` classes on one element would have an unpredictable winner.

The `default` variant is a verified byte-for-byte visual no-op versus the prior hardcoded `rounded-2xl border border-mist p-4 shadow-[var(--shadow-card)]` pattern in `DashboardCard.tsx` — the reviewer independently confirmed `--radius-card: 1rem` equals Tailwind's `rounded-2xl`.

### Badge (Task 4)

**File**: `src/components/ui/Badge.tsx`

**API**: `tone?: 'success' | 'warning' | 'error' | 'info' | 'neutral'` (default `neutral`), `children: ReactNode`. Each tone maps to `bg-{tone}/10 text-{tone}` (neutral maps to `bg-mist text-slate`) — no new colors, reusing the exact opacity pattern already used elsewhere in the app.

### Alert (Task 5)

**File**: `src/components/ui/Alert.tsx`

**API**: `tone?: 'success' | 'warning' | 'error' | 'info'` (default `info`), `inline?: boolean` (default `false`), `className?: string`, `children: ReactNode`. Boxed mode (`inline=false`) renders a bordered `role="alert"` div; inline mode renders a plain `role="alert"` paragraph with tone-colored text only, no box. Both modes append `className` after the tone classes rather than replacing them, so a caller can add context-specific overrides (e.g. a smaller text size inside a narrow popover) without losing the tone styling.

### PageHeader (Task 6)

**File**: `src/components/ui/PageHeader.tsx`

**API**: `title: string` (required, rendered as `<h1 className="font-display text-xl font-semibold tracking-tight text-ink">`), `description?: ReactNode`, `actions?: ReactNode`, `filters?: ReactNode` — all wrapped in a `<div className="space-y-4">` structuring the plan's "Title → Description → Actions → Filters" rhythm.

### StatSummary (Task 7)

**File**: `src/components/ui/StatSummary.tsx`

**API**: `count: number`, `label: string`, `tone?: 'ink' | 'danger' | 'warning' | 'info'` (default `ink`). Renders `<p className="text-sm text-slate"><span className="font-mono text-base font-medium text-{tone}">{count}</span> {label}</p>`.

**Naming correction found during planning**: the approved spec called this primitive `StatTile` and assumed a KPI-card shape. Reading the actual Dashboard widget code during planning found no such card — instead, 5 of the 6 widgets (`LowStockWidget`, `PendingDeliveriesWidget`, `PendingLeaveApprovalsWidget`, `UpcomingAppointmentsWidget`, `PendingLabOrdersWidget`) independently repeat the exact same inline "count + tone + label" line. The primitive was built to match that real, simpler shape instead of the assumed one.
