## The 6 UI primitives (Tasks 2–7)

### Button (Task 2)

**File**: `src/components/ui/Button.tsx`

**API**: `variant?: 'primary' | 'secondary' | 'ghost' | 'danger' | 'success'` (default `primary`), `icon?: boolean` (square icon-only sizing), `loading?: boolean` (swaps children for a spinner, ORs into `disabled`), extends `ButtonHTMLAttributes<HTMLButtonElement>`.

`type` defaults to `'button'` and is destructured out of the JSX spread (`...rest`) before it's applied — spreading `{...rest}` after an inline `type={type}` attribute would silently reset it to the HTML default (`type="submit"`) whenever a caller doesn't pass `type` explicitly, since `rest` would still contain an `undefined` `type` key. Reviewer independently confirmed this ordering is correct in the shipped code.

### Card (Task 3)

**File**: `src/components/ui/Card.tsx`

**API**: `variant?: 'default' | 'nested'` (default `default`), `padding?: 'default' | 'compact'` (default `default` = `p-4`, `compact` = `p-3`, added post-review — see Post-review fixes), `hoverable?: boolean` (adds `hover:shadow-[var(--shadow-card-hover)]`), extends `HTMLAttributes<HTMLDivElement>`.

Deliberately has **no `bg-*` class of its own** — background is always supplied by the caller via `className`, documented inline as a comment explaining why: Tailwind's generated stylesheet orders same-specificity utilities by its own internal rule order, not by className string order, so two competing `bg-*` classes on one element would have an unpredictable winner.

The `default` variant is a verified byte-for-byte visual no-op versus the prior hardcoded `rounded-2xl border border-mist p-4 shadow-[var(--shadow-card)]` pattern in `DashboardCard.tsx` — the reviewer independently confirmed `--radius-card: 1rem` equals Tailwind's `rounded-2xl`.

### Badge (Task 4)

**File**: `src/components/ui/Badge.tsx`

**API**: `tone?: 'success' | 'warning' | 'error' | 'info' | 'neutral'` (default `neutral`), `className?: string` (added post-review — see Post-review fixes), `children: ReactNode`. Each tone maps to `bg-{tone}/10 text-{tone}` (neutral maps to `bg-mist text-slate`) — no new colors, reusing the exact opacity pattern already used elsewhere in the app.

### Alert (Task 5)

**File**: `src/components/ui/Alert.tsx`

**API**: `tone?: 'success' | 'warning' | 'error' | 'info'` (default `info`), `inline?: boolean` (default `false`), `size?: 'xs' | 'sm'` (default `'sm'`, added post-review — see Post-review fixes), `className?: string`, `children: ReactNode`. Boxed mode (`inline=false`) renders a bordered `role="alert"` div; inline mode renders a plain `role="alert"` paragraph with tone-colored text only, no box. Both modes append `className` after the tone/size classes rather than replacing them, so a caller can add context-specific overrides without losing the tone/size styling.

### PageHeader (Task 6)

**File**: `src/components/ui/PageHeader.tsx`

**API**: `title: string` (required, rendered as `<h1 className="font-display text-xl font-semibold tracking-tight text-ink">`), `description?: ReactNode`, `actions?: ReactNode`, `filters?: ReactNode` — all wrapped in a `<div className="space-y-4">` structuring the plan's "Title → Description → Actions → Filters" rhythm.

### StatSummary (Task 7)

**File**: `src/components/ui/StatSummary.tsx`

**API**: `count: number`, `label: string`, `tone?: 'ink' | 'danger' | 'warning' | 'info'` (default `ink`). Renders `<p className="text-sm text-slate"><span className="font-mono text-base font-medium text-{tone}">{count}</span> {label}</p>`.

**Naming correction found during planning**: the approved spec called this primitive `StatTile` and assumed a KPI-card shape. Reading the actual Dashboard widget code during planning found no such card — instead, 5 of the 6 widgets (`LowStockWidget`, `PendingDeliveriesWidget`, `PendingLeaveApprovalsWidget`, `UpcomingAppointmentsWidget`, `PendingLabOrdersWidget`) independently repeat the exact same inline "count + tone + label" line. The primitive was built to match that real, simpler shape instead of the assumed one.

## Post-review fixes

A final whole-branch review (after all 11 tasks were individually reviewed clean) caught four cross-cutting issues no single task review could see, since each depends on comparing a primitive's own hardcoded classes against how a call site tried to override them. All four are fixed except the fourth, which was investigated and confirmed not to be a real bug.

1. **Alert's hardcoded `text-sm` couldn't be overridden (Important).** `QueueStatusIndicator.tsx` passed `className="text-xs"` to shrink the "needs attention" error inside its 320px popover; this silently did nothing, because Tailwind's generated stylesheet orders `text-sm` after `text-xs` regardless of className string order — the same class of bug `Card.tsx`'s own code comment already documents for `bg-*`. Fixed by giving `Alert` an explicit `size?: 'xs' | 'sm'` prop (default `'sm'`) with a `SIZE_CLASSES` record applied in both the inline and boxed branches; `QueueStatusIndicator.tsx` now passes `size="xs"` instead of the ineffective `className="text-xs"`.
2. **Card's hardcoded `p-4` had the same problem (Minor).** `QueueStatusIndicator.tsx`'s popover intended to keep its original `p-3`, but had no reliable way to override Card's baked-in `p-4`. Fixed by giving `Card` an explicit `padding?: 'default' | 'compact'` prop (default `'default'` = `p-4`, `'compact'` = `p-3`); the popover now passes `padding="compact"`.
3. **Badge had no `className` prop, and the Backorder pill was never migrated (Minor).** `Badge` was the only one of the 6 primitives with no escape hatch for a caller-supplied class. Added `className?: string`, appended after the tone classes, same pattern as `Alert`/`Card`. Separately, `CheckoutForm.tsx`'s "Backorder" pill on a cart line that will exceed available stock was still raw Tailwind (`bg-warning/10 ... text-warning rounded-full ... align-middle`) — missed in the original Task 9 pass even though `Badge` was already imported in that same file for the out-of-stock/low-stock pills. Migrated to `<Badge tone="warning" className="align-middle">Backorder</Badge>`, wrapped in the same `<span className="ml-2 inline-block">` pattern already used for the out-of-stock/low-stock badges two sections up in the same file. Label text unchanged ("Backorder").
4. **Button's `rounded-none` vs. its own baked-in `rounded-[var(--radius-control)]` (Minor) — investigated, confirmed not a real bug, no code changed.** The Complete Sale button passes `className="... rounded-none ... md:rounded-[var(--radius-control)] ..."` to `Button`, which always applies its own unprefixed `rounded-[var(--radius-control)]`. The concern was that the mobile full-bleed bar might not actually lose its rounded corners. Investigated directly against the real `npm run build` output (`.next/static/css/*.css`), not by inference: all three relevant rules — the bare `.rounded-\[var\(--radius-control\)\]` (Button's own class), `.rounded-none` (the mobile override), and the media-query-wrapped `.md\:rounded-\[var\(--radius-control\)\]` (the desktop override) — were located by byte offset in the generated stylesheet. Findings: (a) within the unprefixed/base layer, Tailwind v4 orders same-property utilities alphabetically by full class-name string, and `[` (0x5B) sorts before `n` (0x6E), so `.rounded-none` is deterministically emitted *after* `.rounded-[var(--radius-control)]` — at any viewport width, `rounded-none` wins for `border-radius`, giving the mobile bar genuinely square corners; (b) Tailwind always emits variant-wrapped rules (like `md:`) after all unprefixed rules for the same utility family, by design — this is required for responsive overrides to work at all — so at `md:` and above, `.md\:rounded-\[var\(--radius-control\)\]` is emitted after `.rounded-none` and correctly restores the rounded corners on desktop. Both behaviors are deterministic properties of Tailwind's generator, not incidental to this build's file-scan order. Conclusion: the mobile bar is genuinely full-bleed and the desktop button is genuinely rounded, exactly as intended — no fix applied.
5. **Test-count reconciliation (Minor).** Re-ran `npm test` post-fix: 518 tests passed across 20 test files, unchanged from the number already on record (this phase's fixes added no new tests). Stated here as the real, independently re-verified total from an actual test run, not a reconstructed prior-baseline breakdown.
