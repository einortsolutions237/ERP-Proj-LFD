## Spec findings confirmed already-consistent — no new work required

Before building anything, this phase's own investigation re-confirmed several claims about the existing codebase, and each held exactly as stated:

- **Tables already scroll safely** — `NavShell.tsx`'s `<main>` wraps all page content in `overflow-x-auto`, and individual table components additionally wrap their own `<table>` in a local `overflow-x-auto`. No fixed pixel widths exist anywhere; only `max-w-[Xrem] truncate` per cell with a `title` tooltip fallback. Already fine — the real gap was that zero sticky columns, expandable rows, or detail-drawer patterns existed anywhere, not that scrolling itself was broken.
- **Forms are already mobile-safe** — single-column stacking and `min-h-11` touch targets (from Phase 38's earlier fix) were already correct. The real gap was zero *responsive grouping* — every form looked identical regardless of viewport — not breakage.
- **No modal/dialog component exists anywhere in this app.** The only `fixed inset-0` match in the whole `src/` tree is `NavShell.tsx`'s own mobile nav drawer. `DeleteCustomerButton.tsx` uses the browser-native `confirm()`, which handles its own focus and needed no trap. The only two modal-*adjacent* UIs in the entire app are `QueueStatusIndicator.tsx`'s popover and `CheckoutForm.tsx`'s inline customer-picker panel — neither trapped focus before this phase, and there was no larger hidden inventory of broken dialogs to find.
- **The Dashboard's widget grid is already responsive** (`grid grid-cols-1 gap-4 md:grid-cols-2`) — whether it feels intentionally designed per viewport is a Phase 38.4 judgment call, not a structural fix this phase needed to make.
- **Labels are well-covered** (125 `<label` instances across 38 files) but **`aria-label` is thin** (10 instances across 7 files) — a real gap, but explicitly a Phase 38.5 (full WCAG AA pass) concern, not this phase's.
- **`aria-live` is implicit-only** — `Alert`/`ToastProvider` use `role="alert"`/`role="status"`, which carry implicit `aria-live="assertive"`/`"polite"` per the ARIA spec. Arguably already fine; a real screen-reader confirmation is deferred to Phase 38.5 rather than rebuilt now.

Because of these findings, this phase's real scope was three concrete, well-bounded deliverables — not a ground-up responsive rebuild.

## The viewport-verification problem

`resize_window` was confirmed structurally broken before this phase's implementation work began — a 4th consecutive identical failure (after Phases 24, 36, 38): the tool reports success, but `window.innerWidth`/`innerHeight` never actually changes. The decided resolution, named explicitly rather than deferred a 5th time, was **manual, human-in-the-loop verification** for this phase and for Phases 38.4/38.5/38.6 wherever a responsive or viewport-dependent claim is made — a real person resizing a real browser (or checking a real device) and reporting what they actually see, since no automated channel in this environment currently produces trustworthy viewport verification.

**How that resolution actually played out this phase, reported honestly, not softened:**

- **Sticky-column (Products) and FormSection (Staff) collapse/pin behavior were NOT verified across actual viewport widths.** `resize_window` was not retried a 5th time (it would have failed identically). The user was asked directly, in conversation, to perform the two manual checks — but the conversation proceeded before that manual check was completed, and no report of what the user actually saw was ever received for these two items. What *was* confirmed is a narrower, different claim: the underlying CSS (`position: sticky` / `left: 0` / `z-index` on `ProductTable.tsx`'s first column; `display: grid` / `grid-template-columns` responding to the `md` breakpoint via `matchMedia` on `FormSection`) is genuinely active, read directly via `getComputedStyle` at the browser's current fixed viewport (1536px). Confirming a CSS rule is active at one fixed width is **not** the same claim as confirming the visual pin-while-scrolling or column-collapse behavior actually works across widths — that second, stronger claim remains genuinely open.
- **The focus trap (Task 4/5, plus the mid-phase bug fix below) WAS fully and rigorously live-verified** — this did not depend on `resize_window` at all, since it's a keyboard-interaction check, not a viewport-size check. Real `Tab`/`Shift+Tab`/`Escape` keypresses were driven against the live app, with `document.activeElement` read directly after each keypress to confirm exactly which element held focus. `QueueStatusIndicator`'s popover passed all 5 criteria: focus enters the panel, `Tab` cycles forward through only the panel's own controls, `Shift+Tab` wraps correctly from the first control to the last, and `Escape` returns focus to the popover's own trigger button. This is a genuine, evidence-backed pass, not a claimed one.

This asymmetry — one fully verified, two honestly left open — is reported plainly, matching this project's established standard of reporting the `resize_window` gap honestly in Phases 24, 36, and 38 rather than claiming false confidence.

### `useFocusTrap` hook (Task 4)

**File**: `src/hooks/useFocusTrap.ts` (new)
**Commit**: `ce1fd29..e2bd5e4`, review clean (Approved, zero Critical/Important)

A hand-built hook, no new dependency, returning a `RefObject<HTMLDivElement>` to attach to an open panel's container. It confines `Tab`/`Shift+Tab` cycling to the panel's own focusable elements and returns focus to whatever triggered the panel's opening when it closes. The reviewer manually traced the `Tab`/`Shift+Tab` wrap algorithm against a 3-focusable-element simulation and the single-element edge case, confirmed correct in both directions, confirmed no `Escape`/click-outside logic present, and confirmed no stale-closure risk. Two Minor notes were recorded, one flagged specifically for Task 5's reviewer to double-check: the effect returns early (and never retries) if `containerRef.current` is `null` when `active` flips true — fine as long as the container renders in the same commit that flips `active`, which is how both consumers are structured; and the keydown listener is container-scoped rather than document-scoped, a robustness gap versus a fully general trap, unlikely to matter given both consumers are self-contained panels with forced initial focus.

## Mid-phase bug found and fixed: Checkout customer-picker focus-return

During Task 6's live keyboard verification, `CheckoutForm`'s customer-picker panel passed focus-entry and both-direction `Tab`/`Shift+Tab` wrap, but **closing the panel — via either the Close button or Escape — left focus on `<body>` instead of returning it to the trigger button**, unlike `QueueStatusIndicator`'s popover which passed this same check cleanly.

**Root cause, confirmed by reading the source**: `CheckoutForm.tsx` unmounts the "Attach customer"/"Change" trigger button while the picker is open — it's a conditional *swap*, not a hide/show toggle. `useFocusTrap`'s `triggerRef` captures `document.activeElement` (the trigger button's actual DOM node) at trap-open time, but by the time the trap's cleanup effect runs on close, that captured node has already been detached from the DOM by the swap. Calling `.focus()` on a detached node is a silent no-op, so focus fell back to `<body>`.

**Fix** (commit `f0b9ede`): a stable `id` was added to the trigger element, and the cleanup path was changed to re-look up the live node via `document.getElementById` at close time rather than relying on the stale captured reference — combined with a mount-vs-closing-transition-aware ref flag so the lookup only fires on genuine close, not on the trigger's own remount. `Button.tsx` itself did not need to change: the reviewer independently confirmed its existing `...rest` prop spread genuinely forwards an `id` prop through to the real underlying DOM `<button>`.

This fix was reviewed independently and cleanly (Approved, zero Critical/Important): the reviewer traced the full mount/open/close effect-ordering logic directly rather than pattern-matching, confirmed `useFocusTrap`'s own now-superseded stale-ref `.focus()` call is a harmless no-op that resolves before the new effect's real focus call within the same commit's effect flush (no ordering conflict), and confirmed the fix's scope was exactly the one file. The fix's implementer live re-verified both close methods — the Close button and Escape — before the fix went to review, and both were confirmed working correctly.
