# Phase 40.1: Clinical Customer-Detail Design-Primitive Rollout Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Migrate `customers/[id]/page.tsx` (the whole file, not just its clinical parts) and its eleven child/sibling components onto the shared UI primitives (`Button`/`Badge`/`Alert`/`Card`), closing a third of TD-6's seven modules with zero business-logic or capability-check changes.

**Architecture:** Pure rendering-layer refactor — re-parent existing markup onto existing primitives, one file (or tightly-related file pair) at a time. No new components, no new Tailwind tokens, no data-fetching or capability-check changes. Follows the exact discipline of Phase 40 (Roles + Seminars), including its two corrections: primitives are only used where they reproduce the raw markup byte-identically or via an already-established codebase pattern — never forced where the shape, size, or behavior would meaningfully change.

**Tech Stack:** Next.js 16 App Router (Server + Client Components), TypeScript, Tailwind CSS v4, existing primitives in `src/components/ui/`.

## Global Constraints

- **Zero color/font/token changes**, with two already-accepted exceptions carried forward from Phase 40: (a) `Button`'s appearance normalizes onto its established look (text-sm/font-medium/hover-active states) rather than being byte-identical to whatever raw markup it replaces — acceptable, not a regression; (b) `Button`'s `loading` prop replaces submit-button text with an icon-only spinner, which is a real accessible-name gap already tracked as **TD-8** — this phase widens TD-8's affected-call-site count, it does not introduce a new defect.
- **No business logic, data-fetching, or capability-check code changes anywhere in this phase.** Every `hasEffectiveCapability(...)`/`isBranchLocked(...)`/Firestore query stays byte-identical. This is patient-data-adjacent code (clinical records, lab results, patient demographics) — the only thing allowed to change is which component renders a given piece of already-computed data.
- **Do not touch `customers/[id]/page.tsx`'s purchase-history query** (`salesSnap`, lines 81–88) — its branch-scoping logic was deliberately fixed and audited in Phase 33. Only the rendering of the resulting `purchases` array may change.
- **Three deliberate, documented exclusions — do not migrate these, even though they involve color:**
  1. **Dot-badges** (appointment status in `page.tsx`, lab-order status + lab-result flag in `LabSection.tsx`): background tint + a small colored dot span, but the label text itself stays `text-ink`, never the tone color directly. This is a WCAG-AA fix from Phase 15/19.2 — raw `text-success`/`text-warning` failed contrast at badge size when these were built. `Badge` colors its text directly by tone; swapping would silently undo an accessibility fix.
  2. **Colored text-links** ("Edit"/"Delete"/"View"/"Book appointment" — `text-marine` or `text-danger`, no border, `hover:bg-X` or `hover:bg-X/10`): this exact shape is the codebase's already-established non-`Button` convention for row/inline text actions, used identically today in the already-migrated `StaffTable.tsx`. Not a migration gap.
  3. **`text-xs` bordered micro-buttons** (`ClinicalSection`'s per-row "Order lab test", `AttachScanForm`'s "Attach scan", `LabResultForm`'s "+ Add row"/"−" remove-row, `PendingDeliveriesSection`'s "Mark fulfilled"): `Button` has no `text-xs` size option (base is always `text-sm`), and these sit inside table cells and tight form grids where a size bump is a real layout disruption, not a negligible one.
- **`customers/[id]/page.tsx`'s own `<h1>` (customer name) is NOT migrated to `PageHeader`.** `PageHeader`'s `title` prop is typed `string`, and its `<h1>` carries no `truncate`/`min-w-0` classes and accepts no `title=` HTML attribute passthrough. The current raw markup (`min-w-0 truncate ... title={data.name}`) shows an ellipsis-truncated name with a hover tooltip for long customer names — real user data with no length limit. Forcing this into `PageHeader` would silently drop that overflow handling for any customer whose name is long enough to wrap. This stays raw; only the phone/email/notes card below it (Task 1) gets `Card`.
- **Table-wrapper containers stay hand-rolled**, matching the established `StockTable.tsx`/`ProductTable.tsx` precedent used in every prior phase — this applies to the purchase-history table, the appointments table, and the lab-order result tables.
- **No component-rendering test infrastructure exists.** Verification per task is `npx tsc --noEmit` + a code-level check against the exact snippets below; live visual/functional verification happens once, at the end, via the user's own UAT walkthrough — same policy Phase 40 established and the user confirmed.
