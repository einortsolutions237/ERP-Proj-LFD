# Phase 40.2 (Messaging Design-Primitive Rollout) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Migrate the Messaging module (conversation list + thread view) onto the shared design primitives (`PageHeader`/`Button`/`Alert`/`Card`), closing the 4th of TD-6's seven modules, with zero business-logic, data-fetching, or capability-check changes.

**Architecture:** Pure rendering-layer re-parenting — swap existing hand-rolled markup for the equivalent shared primitive from `src/components/ui/`, matching the mechanical, zero-color/font-change discipline every prior design-rollout phase (10, 21, 22, 27, 28, 33, 34, 40, 40.1) has used. No new primitive is created; no existing primitive is modified.

**Tech Stack:** Next.js App Router, TypeScript, Tailwind CSS. Primitives already exist at `src/components/ui/{PageHeader,Button,Alert,Card}.tsx` — read, not modified.

## Global Constraints

- Zero color/font/token changes (per `docs/superpowers/specs/2026-08-02-phase-40-series-ui-ux-refinement-design.md`'s Constraints section) — the one accepted exception is the same one already established in Phase 38.6 (raw `<h1>` → `PageHeader` on `stock/page.tsx`/`pos/sales/page.tsx`), where `PageHeader`'s `tracking-tight` is a byte-for-byte repeat of an already-reviewed precedent, not a new decision.
- No business-logic, data-fetching, or capability-check change anywhere in this phase — `requireCapability('messaging.access')`, the relationship-check logic in `canMessage.ts`/`getMessagingParty.ts`, and both API routes are out of scope and must not be touched.
- `impeccable` used in **audit mode only** (per the series spec) — a consistency/accessibility spot-check, not a new aesthetic decision. `frontend-design` is **not used** in this phase.
- Extra accessibility weight on `ThreadView.tsx` specifically: it already carries Phase 38.5's `aria-live="polite"` fix on the message-list container — the `Card` migration in Task 2 must preserve that attribute exactly, since a regression here would undo real, already-shipped accessibility work (named explicitly in the series spec).
- Review tier: Sonnet-tier review is sufficient for both tasks — this phase touches no Firestore transaction and no money/inventory write, matching this project's established review-tier rule (Opus reserved for high-stakes transactions).
- TD-4, TD-5, TD-7 (unrelated tech debt already flagged elsewhere in Messaging/RBAC) are explicitly out of scope — do not fix, do not investigate further, per the series spec's own "Out of Scope" list.

### Deliberate exclusions (confirmed during planning, hold throughout implementation and audit)

1. **`ConversationList.tsx`'s contact-row `<Link>`** — a full-row navigation link (`flex min-h-11 items-center justify-between ... hover:bg-marine/5`), not an action button and not the colored-text-link pattern either. Matches the existing row-link convention already used by `StockTable.tsx`/`ProductTable.tsx`/`SalesTable.tsx`'s own row links — stays raw.
2. **`ConversationList.tsx`'s `<ul>` group wrapper** (`divide-y divide-mist overflow-hidden rounded-2xl border border-mist bg-surface shadow-[var(--shadow-card)]`, zero padding, per-row `px-4 py-3`) — shape-matches a table wrapper, not a `Card`. `Card`'s `PADDING_CLASSES` only offers `default` (`p-4`) or `compact` (`p-3`); there is no zero-padding variant, and adding one would extend the primitive itself, out of scope for a mechanical rollout. Matches the already-established "table wrappers stay hand-rolled" precedent (Phase 38.4/38.6 left `StockTable`/`ProductTable`'s own wrappers raw for the identical reason).
3. **`ConversationList.tsx`'s "no longer available" inline flag** (`<span className="ml-2 text-xs text-danger">`) — does not byte-match `Badge`'s error-tone classes (`bg-danger/10 text-danger`, `rounded-[var(--radius-badge)] px-2 py-0.5`); the raw span has no background, padding, or rounding. Matches the `ProductTable.tsx` active/inactive-pill precedent (Phase 38.6): when a swap isn't a pure mechanical byte-match, it stays raw rather than introduce a small but real visual change. Named here explicitly so it isn't silently missed.
4. **`ThreadView.tsx`'s "← Messages" back link** (`text-marine ... hover:bg-mist hover:underline`) — the established colored-text-link pattern, the same exclusion category Phase 40.1 named for Edit/Delete/View links. Stays raw.
5. **`FormSection` is not used anywhere in this module** — `ThreadView.tsx`'s compose bar is a single input + button in a flex row, not a two-column field-pair grid, the only shape `FormSection` supports. Matches Phase 40's own precedent that not every primitive applies to every module.
6. **`StatSummary` is not used anywhere in this module** — no stat/count to summarize.

## Task 2: `ThreadView.tsx` — Button, Alert, Card

**Files:**
- Modify: `src/components/messaging/ThreadView.tsx`

**Interfaces:**
- Consumes: `Button` from `@/components/ui/Button` (`variant`, `loading`, `disabled`, standard button props); `Alert` from `@/components/ui/Alert` (already imported in this file — `tone`, `inline`, `role`); `Card` from `@/components/ui/Card` (`className`, plus any native `div` attribute via its `...rest` spread, including `aria-live`).
- Produces: nothing consumed by a later task.

- [ ] **Step 1: Add the two new imports**

At the top of `src/components/messaging/ThreadView.tsx`, alongside the existing `Alert` import:

```tsx
import Button from '@/components/ui/Button'
import Card from '@/components/ui/Card'
```

- [ ] **Step 2: Message-list wrapper `<div>` → `Card`**

Current (`ThreadView.tsx:110-113`):

```tsx
      <div
        className="flex-1 space-y-2 overflow-y-auto rounded-2xl border border-mist bg-surface p-4 shadow-[var(--shadow-card)]"
        aria-live="polite"
      >
```

New — `Card`'s default variant already supplies `rounded-[var(--radius-card)]` (= `rounded-2xl`, both `1rem`), `border border-mist`, `shadow-[var(--shadow-card)]`, and `p-4` (its `default` padding); the caller-supplied classes carry the rest, per `Card`'s own documented contract (background and any extra layout classes are the caller's responsibility):

```tsx
      <Card className="flex-1 space-y-2 overflow-y-auto bg-surface" aria-live="polite">
```

Close the matching tag at the end of the message list (`ThreadView.tsx:129`, currently `</div>`) — change it to `</Card>`. Leave every child of this container (the empty-state `<p>`, the `.map` over messages, each message bubble) completely unchanged.

- [ ] **Step 3: Error `<p role="alert">` → `Alert`**

Current (`ThreadView.tsx:133-137`):

```tsx
          {error && (
            <p role="alert" className="text-sm text-danger">
              {error}
            </p>
          )}
```

New — `Alert`'s `inline` mode with default `size="sm"` and `tone="error"` renders exactly `<p role="alert" className="text-sm text-danger">`, a byte-identical match to the current markup:

```tsx
          {error && (
            <Alert tone="error" inline>
              {error}
            </Alert>
          )}
```

- [ ] **Step 4: Send `<button>` → `Button`**

Current (`ThreadView.tsx:152-159`):

```tsx
            <button
              type="button"
              onClick={handleSend}
              disabled={sending || !draft.trim()}
              className="min-h-11 rounded-lg bg-marine px-4 text-sm font-medium text-paper transition-opacity duration-200 disabled:opacity-50"
            >
              {sending ? 'Sending…' : 'Send'}
            </button>
```

New — `Button`'s default `variant="primary"` is `bg-marine text-paper hover:bg-marine/90 active:bg-marine/80`, a superset of the current classes (it adds the same hover/active feedback every other migrated primary button in this app already has). Pass `loading={sending}` rather than hand-rolling the "Sending…" text swap, matching the established pattern from every prior `Button`-adopting phase:

```tsx
            <Button onClick={handleSend} disabled={sending || !draft.trim()} loading={sending}>
              Send
            </Button>
```

This is call site #15 to pass `loading` to `Button` — Task 3 below updates TD-8's tracked count accordingly. This is `Button.tsx`'s own known, already-documented, already-accepted pre-existing behavior (the spinner replaces `children` entirely rather than sitting alongside it) — not a new defect introduced by this task, and not this task's job to fix.
