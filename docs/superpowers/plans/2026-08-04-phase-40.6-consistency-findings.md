# Phase 40.6: Whole-branch consistency audit — findings

**Scope:** every file touched across Phase 40–40.5 (Roles, Seminars, the clinical-record sections of the customer detail page, Messaging, Accounting, Payroll, Reports), read together as one pass rather than module-by-module, per TD-6's own closure criteria (`docs/tech-debt.md`).

**Method:** `impeccable:impeccable` invoked in audit/critique mode (session had no `PRODUCT.md`; per the skill's own setup step, a scoped audit against existing code proceeds using the code itself as context rather than blocking on `init`). The actual check was systematic grep-then-read: every occurrence of each of the six primitives (`PageHeader`, `Card`, `Button`, `Badge`, `FormSection`, `StatSummary`) across the full file list was located, the canonical class string/prop shape read from an established reference file (e.g. `StockTable.tsx` for table wrappers, `Button.tsx`/`Card.tsx`/`PageHeader.tsx`/`FormSection.tsx` source for primitive shapes), then every other instance diffed against it. Each of the four named exclusion categories was located across the full file set and diffed instance-to-instance, not just checked for internal consistency within one file. Full file list read in this pass (all 30+ files from the brief, across all seven module buckets, plus the two out-of-bucket files and the two carry-forward items) — see the brief for the complete enumeration.

**Observation, not classified as drift, not fixed:** `FormSection` is not used at all in the clinical forms (`DemographicsForm.tsx`, `TreatmentForm.tsx`, `LabOrderForm.tsx`) even though some of their fields are pairable in the same way Accounting/Payroll's fields were (e.g. `DemographicsForm`'s Marital-status/Religion and Occupation/Referral-name). Deciding which two of `DemographicsForm`'s four fields belong together has no established canonical answer to copy from — it would be a new layout decision, not a literal class-string/prop-shape swap, so it falls outside this task's "mechanical primitive-swap, no restructuring" mandate. Noted here rather than silently left out or silently fixed with an arbitrary pairing choice.

## 4. Real drift found and fixed

### `AttachReceiptForm.tsx` micro-button/file-input vs. canonical `AttachScanForm.tsx`

**Classification: (a) real drift, fixed.**

`AttachScanForm.tsx` (Phase 40.1, clinical lab-scan upload) and `AttachReceiptForm.tsx` (Phase 40.3, expense-receipt upload) are the two named instances of the "`text-xs` bordered micro-button" exclusion category doing the *identical* job (a file-picker + an "Attach X" submit button). Phase 40.3's own log entry (`docs/tech-debt.md`) states `AttachReceiptForm.tsx` was "reviewed and needed no primitive change" — true in the sense that neither file needed a `Button`-component swap (both are correctly outside that category) — but the two files were never diffed against each other byte-for-byte, which is exactly the class of gap only a whole-branch pass catches.

Before this fix, `AttachReceiptForm.tsx` differed from `AttachScanForm.tsx` in three ways:
1. **Touch target:** `AttachScanForm.tsx`'s button carries `min-h-11` (the Phase 38-established 44px minimum); `AttachReceiptForm.tsx`'s did not — it used `py-1` instead, rendering at roughly 30px tall, visibly smaller than every sibling micro-button in this category.
2. **Padding:** `px-3` (canonical) vs. `px-2 py-1` (drifted).
3. **Accessible name:** `AttachScanForm.tsx`'s file input has a proper `sr-only` `<label htmlFor={fieldId}>` (`fieldId` built from `useId()`); `AttachReceiptForm.tsx`'s file input had no associated label at all — a real accessible-name gap for a screen-reader user, the same bug class Phase 38.5's mechanical sweep fixed elsewhere in this codebase.

**Fix applied** — mechanical copy from `AttachScanForm.tsx`, adjusted only for the field-specific label text ("Receipt file" vs. "Scan file", content, not styling):
- Added `useId` import and `fieldId` const (`attach-receipt-file-${uid}`).
- Added the `sr-only` `<label htmlFor={fieldId}>Receipt file (JPEG, PNG, or PDF)</label>` and `id={fieldId}` on the `<input>`.
- Changed the button's class string from `shrink-0 rounded-lg border border-mist px-2 py-1 text-xs text-ink transition-colors hover:bg-mist/40 disabled:opacity-50` to `min-h-11 shrink-0 rounded-lg border border-mist px-3 text-xs text-ink transition-colors hover:bg-mist/40 disabled:opacity-50` (byte-identical to `AttachScanForm.tsx`'s button class).

Zero color changes, zero logic changes, zero new component — a literal class-string/markup copy from the file identified as canonical (the more complete, already-touch-target-and-label-compliant sibling). File: `src/app/(dashboard)/expenses/new/AttachReceiptForm.tsx`.

No test file exists for `AttachReceiptForm.tsx` (confirmed by grep — only `ExpenseForm.tsx` references it, and no `*.test.*` file matches it), so there was no existing coverage to re-verify beyond the full suite staying green.
