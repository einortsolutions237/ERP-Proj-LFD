This is the first phase in the series to use `Card` — the customer's phone/email/notes block was confirmed byte-identical to `Card`'s default variant/padding while writing the plan.

**Three deliberate exclusion categories, held throughout and confirmed still raw by both the task reviews and the impeccable audit:**
1. **WCAG-driven dot-badges** — appointment status (`page.tsx`), lab-order status and lab-result flag (`LabSection.tsx`). Text stays `text-ink`, never tone-colored, per a Phase 15/19.2 contrast fix. `Badge` colors text directly by tone, so migrating would have silently undone that fix.
2. **The established colored-text-link pattern** — Edit/Delete/View/Book-appointment links, already the codebase's non-`Button` convention (`StaffTable.tsx` uses the identical shape for its own Edit/Delete).
3. **`text-xs` bordered micro-buttons** — per-row "Order lab test," "Attach scan," "+ Add row"/"−" remove, "Mark fulfilled." `Button` has no `text-xs` size option, and these sit in table cells and tight form grids.

The customer-name `<h1>` header was also deliberately left raw — `PageHeader`'s `title` prop can't reproduce the existing `truncate`+tooltip handling for a long, real customer name, so forcing it in would have been a functional regression, not a cosmetic one.

## `impeccable` audit (Task 9)

Invoked in audit mode against all twelve touched files, with the WCAG dot-badge check as the explicit top priority given this module's higher accessibility stakes. **Found and fixed one real regression**: Task 1's `Card` migration had dropped the phone/email/notes block's `bg-surface` background. `Card.tsx` deliberately excludes background from its own classes (callers must supply `bg-*` via `className`, per the component's own source comment) — a design detail the Phase 40.1 plan's own Task 1 code snippet missed, not something either the Task 1 implementer or its reviewer could have caught from the brief alone. Fixed in `ad73cd3`, verified minimal (one file, one class added) and correct by a scoped re-review.

All three WCAG dot-badge patterns confirmed byte-unchanged across all eight migration commits (text color never changed). All deliberately-excluded text-links and micro-buttons confirmed still raw. `PendingDeliveriesSection.tsx`'s new `STATUS_TONE` map confirmed exhaustive against `PendingDeliveryStatus`'s real two-value union.

## Live UAT (Task 10)

Performed as `super_admin` (logged in by the user, observed via browser automation) against a real customer with clinical/lab/intake history ("Lab Test Only Customer"):

- **Header + Card**: customer name, Edit/Delete links, and the phone/email/notes card all rendered correctly — the `Card` background-fix from the audit confirmed visually correct (the card now stands out with its border/background instead of blending into the page).
- **Clinical record**: "Add treatment" `Button` rendered correctly.
- **Lab orders**: `ORDER_STATUS`/`FLAG` dot-badges confirmed intact (colored dot + `text-ink` label, e.g. "completed"/"normal"); per-order "Enter results" and "Attach scan" confirmed still raw micro-buttons; standalone "Order lab test" `Button` confirmed correct.
- **Pending deliveries**: empty-state text rendered correctly (no deliveries to exercise the `Badge` visually this pass, but the code-level review already confirmed the tone mapping).
- **Patient demographics**: "Record demographics" `Button` (secondary variant) toggled the form correctly; filled in a real value and submitted — confirmed the loading spinner fires, the save succeeds, the page shows the saved data, "Edit demographics" appears afterward, and the `SavedNote` dot-confirmation pattern renders correctly.
- **Nursing visits**: "Record visit" `Button` (primary variant) rendered correctly.

A second, narrower-role pass (e.g. `doctor`/`nurse`) was considered and deliberately skipped: every task review explicitly confirmed none of the eight migration commits touched any `{canX && ...}` capability conditional — only content *inside* an already-passing conditional changed. A narrower role can only ever render fewer sections (guard untouched) or the same now-confirmed-correct primitives; there's no intermediate rendering state only a second role could expose.
