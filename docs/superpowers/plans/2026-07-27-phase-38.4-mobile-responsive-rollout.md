# Phase 38.4 — Genuine Mobile Responsive Rollout Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Checkout, Stock, Products, and Sales Log genuinely usable on a phone — real mobile-first layouts, not desktop layouts surviving only via `overflow-x-auto` horizontal scroll — without changing any business logic, capability gate, or data model.

**Architecture:** Two different problems, two different fixes. Checkout (`CheckoutForm.tsx`) is already single-column below `md` structurally; its real defect is two rows (the catalog-picker item row, the cart line-item row) that pack too many fixed-width elements into one flex row, crushing the product/line name. Those two rows get a mobile-first reflow. Stock, Products, and Sales Log are each a `<table>` with no mobile treatment at all beyond the page-level `overflow-x-auto` safety net (confirmed present on `NavShell.tsx`'s `<main>`, `src/components/layout/NavShell.tsx:94`) — each gets a `md:hidden` card-list view added alongside the existing `hidden md:block`-wrapped table, reusing the existing `Badge`/`Button` primitives so the mobile card and the desktop table stay visually consistent. Per Impeccable's `adapt` reference (`reference/adapt.md`, read this session) and the UI/UX Pro Max product register (`reference/product.md`, read this session): "Tables: Transform to cards on mobile" is the named pattern for exactly this shape, and product-register responsive behavior should be structural (breakpoint-driven layout swap), not fluid typography — which is exactly the split-view approach below.

**Tech Stack:** Next.js App Router, TypeScript, Tailwind CSS (mobile-first `sm:`/`md:` breakpoints — no custom breakpoint tokens found in this codebase, standard Tailwind 640/768/1024). Existing UI primitives only: `Button`, `Badge`, `Card` (all `src/components/ui/`). No new dependencies, no new primitives (see Global Constraints).

## Global Constraints

- No business logic, capability gating, schema, or data-model change anywhere in this phase.
- No new primitives. **Considered and declined**: a shared responsive-table component. Three tables (Stock, Products, Sales Log) now need the identical "cards below `md`, table at `md:` and up" structural split, which might look like it finally justifies one — but each table's row content differs enough (Stock has two inline Adjust/Transfer forms that expand within a row; Products has Edit+Delete; Sales Log has a single View link) that a shared component would need render-prop plumbing to save roughly 15 lines per file. Each table keeps its own inline mobile-card JSX. This is a judgment call, recorded here so a future reviewer doesn't have to re-litigate it from scratch.
- No `resize_window` dependency anywhere in this phase's own verification (it has failed identically four times — Phases 24, 36, 38, and before 38.3 shipped). Every task verifies structurally (build clean, typecheck clean, `hidden`/`md:hidden`/`md:block` class pairing present and mutually exclusive via direct source read) and the phase as a whole closes on one real, blocking human-verification checklist — see Task 5.
- Per CLAUDE.md's Known-issues policy: this phase already touches `src/app/(dashboard)/stock/page.tsx` for mobile work, so Task 2 also fixes the long-flagged boundary bug there — its inline `quantity < reorderThreshold` check gets replaced with the shared `isLowStock()` helper (`quantity <= reorderThreshold`, `src/lib/inventory/lowStock.ts`) that reports and the Cloud Function already use.
- This phase already touches `CheckoutForm.tsx`'s catalog-picker row for mobile work, so Task 1 also fixes a bug Phase 38.1's own completion report logged and explicitly deferred: the out-of-stock/low-stock `Badge`s could get visually clipped by that row's `truncate` wrapper on a long product name. Moving the badges outside the truncated span (still inside the row) fixes this as a structural side effect of the same edit.
- Every task's review is Sonnet-tier — this phase is pure UI/styling with zero transaction or business-logic changes, matching the precedent already set by Phases 38.1–38.3 (no task in that series needed Opus).
- Reuse `Badge`/`Button` exactly where their existing tone/variant already reproduces a screen's current raw-Tailwind markup byte-for-byte (confirmed per task below). Where a primitive's closest tone would visually differ from the existing raw markup (Products' "inactive" pill — `Badge`'s `neutral` tone is `bg-mist text-slate`, not the existing `bg-slate/10 text-slate`), keep the raw markup instead of forcing a primitive, so the same row doesn't show two different-looking status pills between its desktop and mobile rendering.

**Why this reproduces the exact desktop layout unchanged at `sm:` and up, and why it works below `sm:`:** the outer row is `flex-col` (mobile default) / `sm:flex-row sm:items-center sm:justify-between`. Below `sm:`, a flex-column container's children stretch to the full row width by default (`align-items: stretch` is the flex default) — so the new inner `<div className="flex items-center justify-between gap-2 ...">` (quantity controls + price + remove) stretches to the full card width and its own `justify-between` spreads its three children (qty control / price / remove) across that width, giving a real second row instead of three elements crushed against a `flex-1` name. At `sm:` and up, the outer container becomes `flex-row`, so the inner div reverts to its natural (non-stretched) width and sits to the right of the name column exactly as before — and because that div has no `flex-1` of its own, `justify-between` among its three children becomes a no-op once there's no extra space to distribute, reproducing the original tightly-packed right-aligned cluster byte-for-byte. Nothing about `addProduct`, `setLineQuantity`, `removeLine`, `willBackorder`, or any handler changed — only the wrapping `className`s and one extra wrapping `<div>`.
