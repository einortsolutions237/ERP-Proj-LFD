# Phase 40.4 (Reports Design-Primitive Rollout — Mechanical) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Migrate the three Reports pages (Sales, Inventory, P&L) onto the shared design primitives (`PageHeader`/`Button`/`Card`), completing primitive adoption across all seven of TD-6's tracked modules — mechanically only, with zero new visual/creative content. Zero business-logic, data-fetching, or capability-check changes.

**Architecture:** Pure rendering-layer re-parenting, matching every prior mechanical-rollout phase in this series (10, 21, 22, 27, 28, 33, 34, 40, 40.1, 40.2, 40.3). This phase is also the **first to use `PageHeader`'s `filters` prop** — it exists in the primitive's own type signature (`filters?: ReactNode`, rendered below the title/actions row) but has never been adopted anywhere yet; Sales and P&L's date-range `<form>` elements are close to a purpose-built fit for it.

**Tech Stack:** Next.js App Router, TypeScript, Tailwind CSS. Primitives already exist at `src/components/ui/{PageHeader,Button,Card}.tsx` — read, not modified.

## Scope clarification (a real spec inaccuracy, confirmed before writing this plan)

The series spec's Phase Breakdown table describes this phase as "Reports — mechanical primitive rollout (Sales, Inventory, P&L; **4 pages total**)." Direct inspection of the codebase — `src/app/(dashboard)/reports/` and the Sidebar's own Reports/Accounting nav entries (`src/components/layout/Sidebar.tsx:320-330`) — confirms there are exactly **three** report routes (`reports/sales`, `reports/inventory`, `reports/pnl`), no fourth. There is no `reports/page.tsx` landing page and no other report route anywhere in the app. **This plan treats "4 pages total" as a minor spec inaccuracy, not a missing scope item** — three pages is the complete, correct scope, consistent with the spec's own Background section elsewhere noting "Expenses' own list page is its only report view — no separate route exists," which already implies Reports itself has no extra page beyond its three named types. Flagging this plainly per this project's practice of naming spec discrepancies rather than silently reconciling them or inventing a fourth page that doesn't exist.

## Global Constraints

- Zero color/font/token changes — the one accepted exception is `PageHeader`'s `tracking-tight`, an already-established precedent reused in every prior installment of this series.
- No business-logic, data-fetching, or capability-check change anywhere in this phase — `requireCapability`, `buildSalesReport`, `buildInventoryReport`, `buildPnLReport`, `isBranchLocked`, and all three report API routes are out of scope. The `<form method="GET">` elements keep their exact `name`/`defaultValue` attributes and GET-based full-page-reload submission behavior — only their DOM position (now inside `PageHeader`'s `filters` slot) and their internal field markup (adding `id`/`htmlFor`, swapping the submit `<button>` for `Button`) change.
- No new visual/creative content — this is the mechanical-only phase (per the series' own Phase 40.4/40.5 split). Chart additions, layout redesign, and copy changes are explicitly Phase 40.5's job, not this one.
- `impeccable` used in **audit mode only**. `frontend-design`/`dataviz` are **not used** in this phase — they're reserved for Phase 40.5.
- Review tier: Sonnet-tier review is sufficient — no Firestore transaction or money/inventory write is touched (the report-building functions themselves are read-only aggregation, untouched either way).
- Adding `id`/`htmlFor` pairs to the date-range/branch filter fields (which currently lack them) is done incidentally while relocating those exact JSX blocks into `PageHeader`'s `filters` prop — matching the same incidental-fix precedent established in Phase 40.3, not a separate scope expansion.
- This phase does **not** close TD-6 — per the series spec, Phase 40.5 still adds Reports' creative polish (new charts via `dataviz`) before Phase 40.6's whole-branch consistency audit formally marks TD-6 resolved. This phase's tech-debt.md update should say so explicitly, not prematurely declare the module "done."

### Deliberate exclusions (confirmed during planning, hold throughout implementation and audit)

1. **All table wrappers** (`overflow-hidden rounded-2xl border border-mist bg-surface shadow-[var(--shadow-card)]`, appearing 6 times across the three pages: Sales' By-branch/By-payment-method/Top-sellers, Inventory's By-branch/Stock-levels, P&L's Expenses-by-category) — matches the established "table wrappers stay hand-rolled" precedent (Stock/Products/Sales Log/Roles/Seminars/Accounting/Payroll all left theirs raw for the identical reason).
2. **Section `<h2>` sub-headers** ("By branch," "Top sellers," "Stock levels," etc.) — these are in-page section headers, not the page's own top-level title. `PageHeader` is for the page-level `<h1>` only, matching the established pattern (e.g. `ConversationList.tsx`'s "IT Support"/"Contacts" group labels stayed raw in Phase 40.2 for the identical reason).
3. **Sales report's sort-by links** ("Revenue | Quantity," `text-marine underline-offset-2 hover:underline`) — the established colored-text-link pattern, same exclusion category as every prior phase's Edit/Delete/View links.
4. **All empty-state text** ("No sales in this range.," "No stock recorded.," etc.) — plain text, not an `Alert` candidate, matching the established convention across the whole app.
5. **`DownloadCsvButton`** (used on all three pages) — a pre-existing, unrelated component (not one of the six TD-6 primitives), untouched.
6. **Inventory report's low-stock row tinting** (`bg-danger/5`/`text-danger` on table body cells) — a table-internals styling detail, not a `Badge` candidate (doesn't match `Badge`'s pill shape/classes at all), stays raw matching the established "table internals stay raw" precedent.
7. **`FormSection` is not used anywhere in this phase** — Sales' and P&L's filter forms use a compact, always-horizontal `flex items-end gap-2` layout (fields inline, aligned to their labels' baseline), not the vertical/stacked-to-2-col-grid shape `FormSection` targets. Wrapping a filter bar in `FormSection` would change it from "always one row" to "stacks on mobile, grid on desktop," a real behavior change this mechanical phase isn't authorized to make — this is a genuine, considered exclusion, not an oversight.
8. **`Badge`/`StatSummary` are not used anywhere in this phase** — `StatSummary` (read directly: a `<p><span className="font-mono ...">{count}</span> {label}</p>` inline count-line, used only in Dashboard widgets) does not match the report pages' bordered stat-tile shape at all — `Card` is the correct primitive for those tiles, not `StatSummary`. No status pill exists anywhere in Reports for `Badge`.
