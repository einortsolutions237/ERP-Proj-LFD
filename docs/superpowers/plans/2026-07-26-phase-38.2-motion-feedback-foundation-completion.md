# Phase 38.2 — Motion & Feedback Foundation — Completion Report

**Date**: 2026-07-26
**Status**: Complete. Tasks 1-5 each shipped as their own reviewed commit (Approved, zero Critical/Important findings on every task); Task 6 was full-suite/scope verification with no code changes; this is Task 7. Base commit before Task 1: `36f6801`.

## Spec findings confirmed already-consistent — no new work required

Before building anything, this phase's own spec-verification step re-confirmed three claims about the existing codebase, and each held exactly as stated:

- **`duration-200` at 150/150 occurrences across 78 files** — the codebase already uses one single transition duration everywhere a duration class appears.
- **Zero `ease-*` classes anywhere** — no custom or competing easing curves exist to reconcile.
- **Reduced-motion is already handled globally** in `globals.css` — no per-component `prefers-reduced-motion` handling was needed.

These three findings meant the phase's actual scope was narrower than a from-scratch motion system — this phase added the *missing* pieces (pressed states, a toast primitive, an `Alert` role prop) on top of a duration/easing/reduced-motion foundation that was already correct and required no changes.

## What was built

### Button pressed/active state (Task 1)

**File**: `src/components/ui/Button.tsx`
**Commits**: `36f6801..45f22b6`

Each of the 5 existing variants (`primary`, `secondary`, `ghost`, `danger`, `success`) gained an `active:bg-*` class one step darker than its existing `hover:bg-*`, plus `active:scale-[0.98]` applied once across all variants. The pre-existing `transition-colors` was replaced with the combined `transition` utility rather than adding a second, separate `transition-transform` alongside it — avoiding a `transition-property` conflict where two competing transition utilities on the same element can silently drop one of the animated properties. `ButtonProps`' public interface is unchanged; this was a purely internal styling change.

### Alert's new `role` prop (Task 2)

**File**: `src/components/ui/Alert.tsx`
**Commits**: `45f22b6..e6ddd94`

Added an optional `role` prop (`'alert' | 'status'`, default `'alert'`), applied to both of `Alert`'s existing render branches (the inline `<p>` and the boxed `<div>`). Backward-compatible with all 4 existing call sites, none of which pass `role` — they keep the same default `'alert'` behavior they already had.

### Toast primitive (Task 3)

**File**: `src/components/ui/ToastProvider.tsx` (new)
**Commits**: `e6ddd94..bd6b50d`

A single new file containing a Context, the `useToast()` hook, a `ToastItem` presentational piece, and the `ToastProvider` itself. Mounted in the shared dashboard layout, which correctly stays an async Server Component — `getSessionUser()` and the `redirect()` auth-gate logic in that layout were confirmed untouched. Verified via `npx tsc --noEmit` and `npm run build` (all 85 routes) both clean.

Two Minor findings were recorded during this task's review, deliberately not fixed in this phase:
1. `showToast`'s `setTimeout` handle for auto-dismiss is never stored or cleared — harmless today because `dismiss`'s filter is a no-op against a missing id, but it's dead-code-running rather than properly cleaned up.
2. `ToastContext.Provider`'s `value={{ showToast }}` isn't memoized, so consumers re-render on every toast add/dismiss even though `showToast` itself is referentially stable.

Both are deferred to a later triage pass, not silently dropped.

### Wiring into CheckoutForm (Task 4)

**File**: `src/components/pos/CheckoutForm.tsx`
**Commits**: `bd6b50d..8e6ff85`

`showToast('Sale completed', 'success')` fires immediately before `router.push` on the immediate-success sale path; `useToast()` is called unconditionally alongside the component's other hooks. The offline-queue path (`queueOffline()`) deliberately does **not** get a toast call — per the Global Constraints for this phase, a queued sale isn't yet a confirmed success, so surfacing a success toast for it would misrepresent an operation that hasn't actually completed against the server. `npm run build` clean (85 routes).

### Login migration (Task 5)

**File**: `src/app/login/page.tsx`
**Commits**: `8e6ff85..625ab6c`

Login's error message now renders via `Alert` (inline) and its submit button via `Button` (loading-only, without double-passing `disabled` alongside `Button`'s own internal disabled-while-loading logic). `handleSubmit`'s logic and both input fields are byte-identical to before — only the error-message and submit-button markup changed. `npm run build` clean.
