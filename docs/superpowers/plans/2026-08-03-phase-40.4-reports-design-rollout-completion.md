**Scope note, resolved before implementation began:** the series spec's Phase Breakdown table says "4 pages total" for this phase, but only three report routes exist in the codebase (`reports/sales`, `reports/inventory`, `reports/pnl` — confirmed via both the `reports/` directory and the Sidebar's own nav entries). Documented as a minor spec inaccuracy rather than an unmet scope item, both in the plan and now in `docs/tech-debt.md`.

**This is the first phase in the series to use `PageHeader`'s `filters` prop** — it existed in the primitive's type signature but had never been adopted anywhere. Used twice (Sales and P&L), both structurally identical (same form shape, same field classes, differing only in P&L's additional conditional branch selector).

`DownloadCsvButton` was reviewed and left untouched on all three pages — a pre-existing, unrelated shared component (also used on Expenses), out of this phase's file scope. The final review flagged that this phase's own migration makes the touch-target gap between it (~30px) and the newly-44px "View" `Button`s more conspicuous than before — not a new problem, but now recorded as a named carry-forward item for Phase 40.5/40.6 rather than a silent gap.

All six table wrappers, section `<h2>` sub-headers, Sales' sort-by links, empty-state text, and Inventory's low-stock row tinting stayed raw, matching established precedent across the whole series. `FormSection` was deliberately not used — the filter forms' compact, always-horizontal layout doesn't fit `FormSection`'s stacked/2-col-grid shape, a real considered exclusion, not an oversight. `Badge` and `StatSummary` don't apply anywhere in Reports (`StatSummary` was confirmed to be a different shape entirely — a Dashboard-widget inline count line, not a bordered stat tile; `Card` is the correct primitive for the report stat tiles).

Independently re-verified (not just trusted from task reports): grepped all 9 `Card` occurrences and confirmed every one is byte-identical (`padding="compact" className="bg-surface"`), confirmed Sales' and P&L's filter forms are structurally identical apart from P&L's extra branch selector, confirmed zero logic changes via a filtered diff over every business-logic identifier, and confirmed `docs/tech-debt.md`'s claims match the actual code.

Three Minor findings, all fixed in one wave and independently re-verified:

- `DownloadCsvButton`'s exclusion was recorded without explaining why or naming the touch-target delta this phase newly makes visible — fixed with an explanatory sentence and a Phase 40.5/40.6 carry-forward note.
- `docs/tech-debt.md` claimed `filters` "renders cleanly... with no visual clash" — stronger than verified, since live UAT (Task 5) hadn't run yet and this project has a documented multi-phase history of its `resize_window` browser-automation tool failing to actually test narrow viewports. Fixed by rewording to a structural/code-level description (the `flex flex-wrap` wrapper receives a single `<form>` child, so wrap behavior can't engage — matching the pre-migration form's identical non-wrapping shape, not a new regression, but genuinely unverified at narrow widths until UAT ran).
- A third point (the `<h1>` `text-2xl`→`PageHeader`'s `text-xl`+`tracking-tight` size delta) was investigated and confirmed to be the same established convergence every prior phase in this series has made — no fix needed, explicitly confirmed rather than silently skipped.

The re-review confirmed both fixes were factually accurate (independently checked against `PageHeader.tsx`, `DownloadCsvButton.tsx`, and the two filter forms directly) and flagged one trivial residual readability nit — a clause spliced mid-sentence creating mild ambiguity about scope, not a factual error — which was parked rather than looped on, since the re-reviewer explicitly called it non-blocking.
