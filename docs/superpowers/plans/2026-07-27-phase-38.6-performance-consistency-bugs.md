## Pre-planning investigation already done (2026-07-27, this session)

All three "confirm before fixing" tasks were investigated directly before this plan was written, so none of Tasks 3-5 below are hypothesis-shaped — each states the actual confirmed finding:

- **Task 3 root cause, confirmed by reading `src/app/api/staff/[staffId]/route.ts:36-42` directly**: the PATCH handler's super_admin-protection guard checks only `existing.role === 'super_admin'` (the *target* record), never `user.role` (the *actor*). It unconditionally blocks role-change/deactivation of any super_admin-tagged staff doc, regardless of who's making the request — including another super_admin. This exactly matches the phase brief's hypothesis.
- **Task 4 root cause, confirmed via a real diagnostic script against live `erp-lfd`** (temporary, deleted after use, per the project's `verify` skill convention): `getAdminStorage().bucket().exists()` returns `false`. A real diagnostic upload attempt returns a genuine Google Cloud Storage 404: `"The specified bucket does not exist."` This is infrastructure, not code — Phase 30's upload code is unaffected and was already proven correct against the emulator.
- **Task 5 audit, confirmed by reading all four report pages directly**: Sales Report and Inventory (Stock) Report already have CSV export via `toCsv()` + `<DownloadCsvButton>` (`src/lib/csv.ts`, `src/components/reports/DownloadCsvButton.tsx`). P&L Report and Expenses have neither.
- **Task 1 premise check, confirmed via a real Firestore count query against live `erp-lfd`** (2026-07-27): `products: 5, services: 1, productStock: 7, sales: 26, stockMovements: 61, branches: 2, customers: 9`. Nowhere close to the "a few hundred rows" threshold Phase 38.4's own report named as the point where the Stock/Products/Sales Log card+table DOM-doubling pattern would be worth revisiting.

## ⚠️ Design call in Task 3 — needs your confirmation before dispatch, not just mine

The current guard's behavior (block *everyone*, including another super_admin, from changing a super_admin-tagged account's role/status) is consistent with CLAUDE.md's own stated Permissions design: *"super_admin (protected, immutable, cannot be demoted or deleted in-app)"* — no stated exception for another super_admin acting. Task 3's fix as scoped below **loosens that**: a non-super_admin actor stays fully blocked (the "protected from everyone else" property is preserved), but a super_admin actor gains the ability to change another super_admin-tagged account's role or deactivate it, through this endpoint. That is a real, deliberate change to a previously-documented security invariant, not a pure bug fix restoring old intended behavior — implementing it means CLAUDE.md's Permissions section needs a one-line update alongside the code (included in Task 3 below). If this reading is wrong and the absolute block was actually intentional, the real fix is different (e.g., a clearer 403 message plus a UI affordance that explains *why*, not a loosened guard) — flag that back instead of proceeding, per the phase brief's own instruction not to force a fix to match a guess.
