## A real mid-implementation correction, brainstormed and resolved before it could propagate

The approved design specified `marine` (`#0f5c66`) for Sales/Inventory chart bars. Task 1's own mandated `dataviz` palette-validation step (a real gate the brief explicitly said not to skip) found `marine` fails the chroma floor on its own — 0.07, below the 0.1 threshold, reading as gray when used as a large filled area rather than the thin strokes/borders it's used as everywhere else in this app. This wasn't a false positive from pairing: independently re-validated alone, marine failed identically; `brass` (P&L's color) alone passed chroma but WARNed on contrast (2.96:1, below 3:1 — legitimately covered by this design's own table-below-every-chart pattern, the validator's own stated exception). `info` (`#2563eb`), an already-locked but previously chart-unused token, passed every check cleanly, alone and paired with `brass`.

This was presented to the user directly with a recommendation before any downstream task consumed the color, confirmed, and both the design spec and implementation plan were corrected (commit `2254adc`) before Tasks 2-4 were dispatched — so every subsequent task built on the corrected color from the start, with zero rework needed later. The correction is documented in both the design spec's own correction note and `docs/tech-debt.md`'s Phase 40.5 entry, as a real, reusable lesson: an already-locked token being safe in its existing UI role (buttons, links, text) doesn't mean it's safe in a new role (a large filled chart mark) — new use cases need their own validation, not inherited trust.

## Final whole-branch review

Dispatched on the most capable available model. Zero Critical, zero Important findings across the whole 7-commit diff. Independently re-verified rather than trusted from task reports: read every one of the 10 `Card` wrappers across all three pages for `bg-surface` (this exact class was Phase 40.1's own real regression), confirmed the exact 4-to-1 `info`-to-`brass` color split holds, confirmed zero business-logic diff via `git diff --stat` against `src/lib/reports/`, and independently re-ran `tsc`/the full test suite rather than trusting the 553/553 claim.

Six Minor findings, four fixed in one wave and independently re-verified:

- **Fixed**: `CategoryBarChart`'s Y-axis `width={56}` could clip large FCFA totals once thousands separators pushed the tick label past 56px — changed to `width="auto"`.
- **Fixed**: the two by-branch charts (Sales, Inventory) rendered a single, comparison-free bar in this app's current single-branch reality — guard changed from `length > 0` to `length > 1` on those two specifically (the other three charts, which are rankings/breakdowns rather than branch comparisons, keep `length > 0`).
- **Fixed**: none of the five new charts had an accessible name — added a required `ariaLabel` prop to both chart components, applied as `role="img"`/`aria-label` on each container, with all five call sites updated to a descriptive label (the top-sellers chart's label correctly branches on the active sort, matching its existing `valueLabel` behavior).
- **Fixed**: a stale `'#0f5c66'` example hex left in the plan doc's Task 1 section after the color correction, corrected to `'#2563eb'`.
- **Deferred (accepted tradeoff)**: both chart components initialize their `prefers-reduced-motion` state to `false` and correct it in a post-mount `useEffect`, so a user with the OS preference enabled sees one frame of the entrance animation before it's suppressed. The reviewer noted a proper SSR-safe fix is genuinely awkward (a lazy initializer touching `window` breaks prerendering) and this reads as an accepted tradeoff, not an oversight — not fixed.
- **Deferred to Phase 40.6**: `BarChartDatum` is declared identically in both new components rather than shared from one location — the reviewer explicitly recommended hoisting this during the upcoming whole-branch consistency audit rather than fixing it here.

The re-review confirmed all four fixes were genuinely addressed with no new breakage, and specifically verified Finding 3 (the widest-reaching fix) touched exactly the 5 real call sites with no missed 6th.
